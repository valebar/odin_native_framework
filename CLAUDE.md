# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
Experimental "native views" framework for Odin, targeting macOS, iOS, Android, Linux and Windows. It follows the Kotlin/Native approach: no codegen and no JS bridge. Odin code calls AppKit/UIKit directly through Objective-C interop, Android views through JNI, and GTK4 and Win32 through plain C bindings. Widgets so far: a vertically scrolling list (NSTableView / UITableView / ListView / GtkListView / SysListView32), a text label (optionally a heading), a single-line text input (NSTextField / UITextField / EditText / GtkEntry / Edit), a push button (NSButton / UIButton / Button / GtkButton / Button), a custom-drawn canvas (NSView / UIView subclasses, a View subclass, GtkDrawingArea, a GDI+ window), an image loaded from bytes, a file or a URL (a drawn NSView subclass / a UIImageView subclass / an ImageView subclass / GtkDrawingArea / a GDI+ window; the canvas draws the same bitmaps), Flutter-style Row / Column stacks (NSStackView / UIStackView / LinearLayout / GtkBox / a hand-written layout window on Windows), a Flutter-style Container with margin, border, background, rounded corners, padding and an optional fixed size around one child (an NSView holding an NSBox / a UIView with a CALayer / an nv.NvContainerView FrameLayout with a GradientDrawable / a GtkBox styled by a per-widget CSS rule / an NVContainer window painted with GDI+), a push/pop page stack (UINavigationController / the ActionBar's up arrow and the Back key / a back button in the title bar on macOS and GTK, an in-window bar on Windows), per-page bar actions (right bar button items / options menu items / GtkHeaderBar buttons / a trailing titlebar accessory / buttons in the Windows bar), an in-view dialog, modal or not (a card over the page inside the window: NSBox / UIView / FrameLayout on the decor view / GtkOverlay child / a child window of the Windows host), and a theme: light / dark / system mode, an accent and default text styles, plus a per-widget `Text_Style` (size, weight, italic, color in the system font, or a custom font loaded from bytes or an asset file: CGFont+CTFont / Typeface / fontconfig / AddFontMemResourceEx). The layout is Flutter-style: one shared app, framework backends per OS, and per-OS host folders that only handle packaging.

## Commands
One build tool, `tools/nvbuild` (an Odin program, so Odin is the only prerequisite), replaces per-OS scripts:
`odin run tools/nvbuild -- [build|check|clean|test|ci] [--platform=windows|macos|ios|android|linux|all] [--release|--debug] [--no-run] [--sim="iPhone 17"] [--avd=Pixel_10] [--device=<serial>] [--team=<id>] [--any-odin]`.
`build` (the default) compiles `app/` for the platform (this host when none is given), packages it and runs it with the console attached; `--release` is `-o:speed` instead of `-debug`, `--no-run` stops after packaging. `check` type-checks `nv` and `app` with `-vet -strict-style` for one target or, with `all`, every target (iOS as both the simulator and the device subtarget) plus `tools/nvbuild` and `android/jnigen` (the cross-target checks work from any host; the Android one only needs the `ODIN_ANDROID_*` variables to be set, which the tool does with placeholders when there is no SDK). `clean` removes `build/<platform>` or all of `build/`. Every spawned command is echoed with a leading `+`, and the first failing one ends the build with its exit code. `odin run` leaves the tool's binary (`nvbuild`, gitignored) in the cwd; the package is not called `build` because that name would collide with the output directory. Every command but `clean` first checks that the compiler that built the tool (`ODIN_VERSION_HASH`) and the `odin` on PATH are both the pinned one (`ODIN_PIN` in `tools/nvbuild/main.odin`, `dev-2026-09-nightly:a2fb372`); `--any-odin` skips the check. The pin moves only on purpose: how the compiler links a shared library decides how `libapp.so` starts on Android.
- macOS: `build/macos/example`.
- iOS simulator: `build/ios/NativeList.app` (Info.plist and assets inside, ad-hoc signed, installed on the `--sim` simulator, a name or a UDID, booted first and unambiguous when several are booted, and launched with a console attached). Screenshot the simulator: `xcrun simctl io booted screenshot build/ios/shot.png`
- iOS device (`--platform=ios --device=<name|udid>`, a paired physical device from `xcrun devicectl list devices`; never auto-detected, since paired devices also show up over Wi-Fi): `build/ios/device/NativeList.app`, built with `-subtarget:iphone`. `ios/Info.plist` is the simulator's, so the copy gets `iPhoneOS` as its supported platform, and the dSYM is moved out of the bundle. Signing needs no configuration (`ios_signing` in `tools/nvbuild/apple.odin`): it takes the first development provisioning profile in Xcode's profile directories that is not expired, covers the bundle id (an exact app id over a wildcard) and the device, and lists a certificate that `security find-identity` has as a valid identity; `--team=<id>` narrows it to one team. The profile is embedded, the entitlements (`application-identifier`, team, `get-task-allow`) are generated, and `codesign` gets the certificate's SHA-1 (names repeat in a keychain). Install and launch are `xcrun devicectl device install app` / `device process launch --console --terminate-existing` (the phone must be unlocked). With no fitting profile the build stops: Xcode has to create one (automatic signing on a project with the bundle id, run once on the device).
- Android (default AVD `Pixel_10`; the `Pixel_8a` image is incomplete): the SDK comes from `ANDROID_HOME` / `ANDROID_SDK_ROOT` or the host's default install location, the NDK and build-tools are the highest installed, the JDK from `JAVA_HOME` (else Homebrew's openjdk@21 on macOS, else PATH). It compiles the Java shims, regenerates the JNI wrappers (`android/jnigen`, needs `javap`), builds `libapp.so`, and packages it without Gradle (d8 → aapt2 → `jar` → zipalign → apksigner; d8 and apksigner are run through `java` since they are batch files on Windows, and the debug keystore is created with `keytool` when missing), installs and launches on `--device=<serial>` (from `adb devices`), else on the only attached device; with none it starts the `--avd` emulator and waits for `sys.boot_completed`, with several it stops and asks for `--device`; every adb call passes `-s`. App stdout goes to `adb -s <serial> logcat -s nv`. Screenshot with `adb exec-out screencap -p > build/android/shot.png`; `adb shell input tap/swipe` can drive the UI.
- Linux: `build/linux/example` against GTK4. Only the GTK4 and libcurl runtimes are required: without `libgtk-4-dev` / `libcurl-dev` the tool symlinks `libgtk-4.so.1` / `libcurl.so.4` (and the pango / fontconfig libraries) into `build/linux/libs` for the linker. Under Hyprland, screenshot with `grim -g "$(hyprctl clients -j | jq -r '.[] | select(.class=="example") | "\(.at[0]),\(.at[1]) \(.size[0])x\(.size[1])"')" build/linux/shot.png` (select by class: the title changes with the page).
- Windows: `build\windows\example.exe` with the manifest from `windows\app.rc` embedded. To screenshot, get the window rect from `(Get-Process example).MainWindowHandle` with `GetWindowRect` (after `SetProcessDPIAware`) and use `System.Drawing.Graphics.CopyFromScreen`.
- Tests: `test` runs `odin test nv -vet -strict-style -define:ODIN_TEST_THREADS=1 -define:ODIN_TEST_FAIL_ON_BAD_MEMORY=true -out:build/<host>/nv_test` (one thread, since the core is package globals; a leak or a bad free of what the core allocates with `context.allocator` fails its test, while the heap and the scopes' arenas are not tracked; on Linux plus the `-L build/linux/libs` flag of `build`). The tests (`nv/*_test.odin`) run the core against a mock backend, so they need no window; one test by hand: add `-define:ODIN_TEST_NAMES=nv.test_push_and_pop`. They only cover the core's side of the backend contract: every backend still needs its click-through on a device. `ci` is `check --platform=all`, then `test`: the safety net before a push, since there is no hosted CI; `tools/hooks/pre-push` runs it once a clone opts in with `git config core.hooksPath tools/hooks` (`git push --no-verify` skips it).
- Compiler pin: to move `ODIN_PIN`, install the candidate and pass `--any-odin` to every command, then (1) `check --platform=all` and `test` pass; (2) host canary: `mkdir -p build && odin build tools/nvbuild -build-mode:shared -out:build/libcanary.so && readelf -d build/libcanary.so | grep -E '\((INIT|FINI)\)'` lists both from `085af86da` on; (3) with the NDK, the Android build prints `libapp.so has DT_INIT`; (4) on a device, `adb logcat -s nv` shows no `no DT_INIT` line, and a Theme switch to Dark, rotation, and Home + relaunch with "Don't keep activities" on (`adb shell settings put global always_finish_activities 1`, which destroys the Activity but keeps the process) behave as before; (5) build the desktops where available. Then set `ODIN_PIN` to the new `odin version` text.
- The example app's Bench action (root bar) pushes a page that times the canvas draw path: each button repaints a fixed workload for 60 frames and prints the average ms inside `on_draw` and per frame.

## Layout
- `app/`: shared user app. It must stay free of platform code.
- `nv/nv.odin`: the shared public API (`run`, `push`, `pop`, `Page`, `Page_Handle`, `Build_Proc`, `page_set_title`, `page_set_actions`, `Action`, `Icon`, `list_create`, `list_view`, `list_reload`, `Item`, `List`, `row_create`, `column_create`, `flex_create`, `Flex`, `Flex_Child`, `Axis`, `container_create`, `container_view`, `container_set_color`, `Container`, `Container_Handle`, `Insets`, `insets_all`, `insets_symmetric`, `label_create`, `label_view`, `label_set_text`, `Label`, `Label_Handle`, `input_create`, `input_view`, `input_text`, `input_set_text`, `Input`, `Input_Handle`, `button_create`, `button_view`, `button_set_title`, `Button`, `Button_Handle`, `canvas_create`, `canvas_view`, `canvas_redraw`, `Canvas`, `Canvas_Handle`, `Painter`, `Color`, `Pointer`, the draw procs (`fill_rect`, `stroke_rect`, `draw_line`, `fill_ellipse`, `stroke_ellipse`, `draw_text`, `draw_image`), `Bitmap`, `bitmap_from_bytes`, `bitmap_from_file`, `bitmap_fetch`, `bitmap_free`, `Font`, `font_from_bytes`, `font_from_file`, `font_free`, `image_create`, `image_view`, `image_set_bitmap`, `Image`, `Image_Handle`, `Fit`, `dialog_show`, `dialog_close`, `Dialog`, `Dialog_Button`, `Dialog_Handle`, `theme_set`, `theme_set_mode`, `theme_mode`, `theme_dark`, `theme_palette`, `Theme`, `Mode`, `Palette`, `Text_Style`, `Weight`, and `View`, an opaque NSView*/UIView*/jobject/GtkWidget*/HWND). It reaches the platform through `g_backend` (`backend.odin`), bound to each backend's `_`-prefixed procs (`_fetch_start` in `fetch_thread.odin` on Windows and Linux, `fetch_darwin.odin` on Apple, over `_http_get` / `_post_main`), and calls the `_`-prefixed draw procs directly. `Item` is the list-row data struct; `Row` is reserved for the layout vocabulary. Every widget has one shape: `X` struct, `x_create(X) -> ^X_Handle`, `x_view(h)`, `x_set_y(h, ..)`. Only Row/Column return a plain `View` (no handle): children are fixed at creation, like Flutter. Pages follow the same shape: `run(Page)` / `push(Page) -> ^Page_Handle`, `Build_Proc` receives the handle, `page_set_title` / `page_set_actions(h, ..)`.
- `nv/*_test.odin`: the core's tests. `#+build-project-name nv` keeps them in `odin check nv` / `odin test nv` (so `check` vets them on every target) and out of every app build (project `app`), so no app links `core:testing`. `mock_test.odin` is the mock backend (`mock_backend`, installed by an `@(init)` and by `mock_begin`): it logs every call that does something (`expect_log` compares the exact, ordered list; the pure queries only answer), makes fake `Mock_View`s in the current scope that a disposer releases (`mock.views` counts the live ones), checks the core's preconditions per call (`mock_require`), answers from `mock.*` fields (`nav_pop_ok`, `decode_ok`, `font_ok`, `asset`, `system_dark`, `system_accent`) and retires a popped page's or a closed dialog's scope at once (`.Now`: macOS, Android, iOS dialogs and back / swipe pops, GTK pages with no slide running) or later at `mock_retire_parked` (`.Later`: GTK after a slide and GTK dialogs from an idle, Windows after `DestroyWindow`, iOS pages popped by `pop()`). `Mock_Page` / `mock_page` script a page's `build` (push, dialog, pop, title) and `Mock_Dialog` / `mock_show` a dialog; `mock_begin` resets every core global, `mock_end` closes what is left the way the app's exit would and fails on live views. A test plays the platform: `callback_enter` / `callback_exit` around a step stand for the native callback it runs in.
- `nv/backend.odin`: the backend contract. `Backend` has one field per operation the core asks of a platform, with the backends' exact signatures; `g_backend` binds them to the `_`-prefixed procs, so a missing or mistyped one fails `check` for its target. The core calls `g_backend.x(..)`; a backend calls its own `_x` directly. The seven draw procs are not in it (the canvas hot path); the tests install a mock.
- `nv/*_macos.odin` (with `appkit_macos.odin`) and `nv/*_ios.odin` (with `uikit.odin`), plus the shared `appkit.odin` and `cg.odin`: the platform backends (`list_*`, `flex_*` for Row/Column, `label_*`, `input_*`, `button_*`, `canvas_*`, `image_*`, `nav_*`, `app_*`).
  - The macOS files carry `#+build darwin:default` and the iOS files (and `uikit.odin`) `#+build darwin:ios`. `darwin:default` matches only a build without `-subtarget` (macOS), `darwin:ios` matches both `-subtarget:iphone` and `-subtarget:iphonesimulator`, and a plain `darwin` matches all three; `darwin:iphone` alone would leave out the simulator. These subtarget tags are in the compiler (`src/parser.cpp`) but not in Odin's docs, so `check` covers macOS, the simulator and the device: a wrong selection fails as a redeclared or undeclared `_` proc. `IS_IOS` remains in `cg.odin`: two in-proc branches and the file-scope `Sys_Font` / `Sys_Color` aliases (`UI_Font` / `UI_Color` from `uikit.odin`, `NS_Font` / `NS.Color` from `appkit_macos.odin`).
  - `send`, `ns_string` and the Auto Layout helpers (`Layout_Constraint`, `flex_link_sizes`, `Layout_Anchor`, the `anchor_*` getters, `layout_pin_edges`, `layout_dialog_card`) in `appkit.odin` (`#+build darwin`, with `container_intrinsic`) are shared by both backends, as is all of `cg.odin` (CoreGraphics bindings, the draw procs, and the image decode / download helpers); the AppKit-only bindings are in `appkit_macos.odin`. `objc_send` needs a typed receiver (`^NS.Object`, not `NS.id`).
- `nv/*_android.odin` / `jni.odin` / `jni_api_android.odin` (generated, see Android JNI below): the Android backend (`#+build linux:android`). The Apple files carry `#+build darwin:default` (macOS) or `#+build darwin:ios`, the shared `appkit.odin`, `cg.odin` and `fetch_darwin.odin` `#+build darwin`.
- `nv/*_linux.odin` / `gtk.odin`: the Linux GTK4 backend (`#+build linux:default`). As on Darwin, a subtarget build tag picks the backend.
- `nv/*_windows.odin` / `win32.odin`: the Windows backend (`#+build windows`). Bindings come from `core:sys/windows`; `win32.odin` holds the shared state (`g_windows`), helpers (`wstr`, `px`, fonts) and the few missing declarations.
- `nv/android/java/nv/`: the generic Java embedder. `NvActivity` loads `libapp.so`, forwards the Back key and the ActionBar's up arrow to `nativeOnBack`, and its options menu to `nativeOnCreateMenu` / `nativeOnAction`; `NvListAdapter` forwards `BaseAdapter` and click callbacks, and `NvInputListener` forwards `TextWatcher` / `OnEditorActionListener`, `NvClickListener` forwards `View.OnClickListener`, and `NvCanvasView` forwards `onDraw` / `onTouchEvent`, to exported `Java_nv_*` procs. Java is only used where Android requires a subclass.
- `ios/`, `android/`, `windows/`: host packaging files only (`Info.plist`, `AndroidManifest.xml`, `app.rc` + `app.manifest`); `tools/nvbuild/` is the build tool (see Commands) and `android/jnigen/` the JNI wrapper generator.

## Backend patterns
- **Delegate classes:** ObjC classes are registered at runtime through `objc_class(&cache, name, super, methods, protocols)` in `appkit.odin` (shared by both Apple backends; `objc_allocateClassPair` + `class_addMethod` + `objc_registerClassPair` once, `cache` is the file's `X_class` global), with `Objc_Method{sel, imp, types}` entries: `proc "c"` IMPs passed through `auto_cast` and arm64 type encodings (for example `"q@:@"`).
  - `objc_alloc_with_handle(cls, h)` is `class_createInstance` with the handle pointer in the indexed ivars (a view subclass still needs its `initWithFrame:`), and `objc_handle(self, X_Handle)` reads it back in an IMP, which then restores `context = h.ctx` before calling Odin code. The app-level singletons (`NVNavTarget`, the iOS app / scene delegates) have no ivars and use `g_app.ctx` / `g_macos.ctx`.
- **App builder:** `run` takes a `build` proc because UIKit views can't exist before `UIApplicationMain`. `run` appends the root page to `g_nav` and calls `g_backend.run()` (`_run`), which takes no arguments: each backend calls `theme_start()` and `nav_show_root()` (bracketed) once views can exist (Android: from the first `onCreate`, after `run` returned). iOS instead builds the root itself (`nav_build`, then `nav_flush_pending`), since `UINavigationController` takes its root controller up front, so the root never reaches `_nav_push`.
  - On iOS the root view sits in a plain container view pinned to its `safeAreaLayoutGuide`, since a stack view would slide under the navigation bar.
  - iOS uses the UIScene lifecycle. `NVSceneDelegate` is named in `ios/Info.plist`, and the names must match `app_ios.odin`.
  - Scene and app delegates are created by UIKit, so they use package globals (`g_app`) instead of ivars.
- **Row height:** on iOS rows are self-sizing and `item_height` is only an estimate. At a fixed 44pt, UIKit's subtitle configuration hides the secondary text.
- **Strings:** use `ns_string`, which copies and autoreleases. `initWithOdinString` does not copy.
- **Temp memory:** only `callback_exit` (`nv.odin`) calls `free_all(context.temp_allocator)`, when the outermost callback returns. Every entry from the platform that allocates or calls the app (`build`, row/select callbacks, `input_notify`, `button_notify`, `on_pop`, `on_close`, the back button / key handlers that call `pop`, the Win32 flex / nav / dialog `WM_SIZE`) is bracketed by `callback_enter()` / `defer callback_exit()`. `push`, `pop`, `dialog_show` and `dialog_close` themselves are app-called and don't bracket. Callbacks nest (an `on_click` that calls `input_set_text`, `list_reload` or `push`, a Win32 layout re-entering nested Row / Column procs), so an inner free would wipe the outer caller's strings. Procs the app calls never free.
- **Scopes (`scope.odin`):** every page (`Page_Handle.scope`, from `nav_page_new`) and every shown dialog body (`Dialog_Handle.scope`, from `dialog_present`, which sets `g_scope_override` while it builds the title / buttons / Row / Column) owns a `Scope`: a growing `core:mem/virtual` arena plus a LIFO list of disposers. `*_create` allocates its handle with `scope_new_in(T)` in `scope_current()` (the override, else the top of `g_nav`, which is the page being built during `build`), so widgets made in `build`, in a callback, or for a dialog's `content` belong to the top page. `context.allocator` is never replaced, so the app's allocations and `h.ctx` are untouched. Disposers (`scope_on_dispose(fn, data)`) release what a handle holds outside the arena: the heap label text / button title (`runtime.heap_allocator()`, since the setters reallocate), `font_free` / `bitmap_free`, and the backend's native references. The rule is that whoever creates a native reference registers its release; parents keep only their own retains (`addSubview`, `addView`, GTK parenting), so a page root is no longer released specially. Apple: `objc_own(obj)` (`appkit.odin`, shared) autoreleases the creator's +1 (autorelease, since the pop may run inside the object's own action), and `objc_clear_delegate_on_dispose` / `objc_clear_data_source_on_dispose` nil the weak slots. Android: `android_own_ref(env, obj)` (`app_android.odin`) is a global ref that the scope deletes. Linux: the container's CSS provider is removed from the display and unreffed. Windows: `Flex_Data` lives in the arena. The backend calls `scope_retire(s)` once the tree is really gone: macOS / Android in `_nav_release` / `_dialog_close`; iOS in the page controller's `didMoveToParentViewController:nil` (`page_did_move`), which UIKit sends once the popped controller has really left, after its transition and after any transition queued behind it: a programmatic `pop` parks the scope in `g_app.retiring` (with the retained controller) until then, a back button or swipe retires it from inside that call (`g_app.removing`); Linux right after `gtk_stack_remove` (`g_linux.dying` keeps `Linux_Dying{root, scope}`), and for a dialog from an idle queued after the card's unref; Windows in `WM_NV_DESTROY` after `DestroyWindow` (the scope rides in `wparam`; its `WM_NCDESTROY`s still read the handles). Inside a callback, `scope_retire` only queues: the outermost `callback_exit` destroys the queued scopes (`scope_flush_retired`) before freeing the temp allocator. So handles stay valid through `on_pop` / `on_close` and until the callback that popped returns. An image's download (`Image_Fetch`, on the heap) is detached by `image_dispose` (`fetch.h = nil`), and so is a canvas's queued redraw on macOS (`Apple_Canvas_Redraw`, by `apple_canvas_dispose`, which on iOS invalidates the canvas's display link).
- **`objc_send` arguments:** literals must be typed (`NS.BOOL(true)`, `NS.Integer(0)`), and nil object arguments are passed as `NS.id(nil)`.
- **Android startup:** the runtime's `_odin_entry_point` runs the `@init` procedures (without them `os.stdout` is nil and fmt prints nothing) and then the app's `main`; it should be `libapp.so`'s DT_INIT, run by `System.loadLibrary` in `NvActivity`'s static initializer. Odin before `085af86da` (the pinned dev-2026-09 included) spawns the linker without a shell, so `-Wl,-init,'_odin_entry_point'` reaches LLD with its quotes and DT_INIT is silently left out (desktop shared libraries lose it too; it is not an Android trait). Both cases work: the `@(init)` proc `android_runtime_started` sets `g_android.started`, and the first `jni_on_create` that finds it unset runs the entry through `dlsym`, before it stores the env and the Activity. So `main` never has a JNIEnv or an Activity: `run` returns at once (`_run` only keeps `g_android.ctx` and pipes stdout to logcat), and before its first Activity the app calls only `theme_set` / `theme_set_mode` (a JNI call traps with a log line in `jni_fn`; `theme_dark` / `theme_palette` answer light with no system accent). The first `onCreate` runs `theme_start` and `set_content`; a later one in the same process (`g_android.shown`: a night-mode or other configuration recreation, or the Activity destroyed while the process lived, as with Developer options' "Don't keep activities"; Back on the root does not do it on API 31+, where it only moves the task to the back) swaps the Activity global ref, resets the stack to the root, calls `theme_notify` and builds the root page again, so `build` runs once per Activity. The Android build prints whether `libapp.so` has DT_INIT. The `main` link name is reserved. `android:configChanges` in the manifest keeps rotation from recreating the Activity.
- **Android build quirks:**
  - `core:thread` needs `pthread_setcancelstate`, which Android's libc lacks, so use raw `posix.pthread_create`.
  - The build tool links an empty stub `libpthread.a`.
  - Odin wants a `darwin-aarch64` NDK toolchain, so `ODIN_ANDROID_NDK_TOOLCHAIN` points at `darwin-x86_64`.
  - A stub `android_main` satisfies `native_app_glue`, which Odin always links.
- **Android JNI:** every Java member is called through a typed wrapper in `nv/jni_api_android.odin` (`view_set_padding(env, v, l, t, r, b)`, `text_view_set_text(env, v, text)`, `paint_style_value_of(env, "STROKE")`, ..), **generated** by `android/jnigen` (an Odin program the build tool runs before `odin build`) from `nv/android/jni_api.txt`: one `class member` line per member in Java syntax (`<init>(..)` for constructors, `.field` for fields, an optional return type to disambiguate overloads, `= name` to override the Odin name), with every descriptor taken from `javap -s` over `android.jar` plus the compiled `nv/*` shims, so a misspelled or missing member fails the build instead of crashing the app. The generated file is committed (so `odin check` works without the SDK); to call a new member add its line and rebuild (or run the generator by hand, see its header). No descriptor is written by hand: `jni.odin` only has `jni_new_object` / `jni_call_*` / `jni_get_*_field` over a `Jni_Method` / `Jni_Field` (class global ref and ID resolved once, on first use; the wrapper names the *declaring* class, whose method ID works on subclass instances), the ref / string / byte[] helpers, and `jni_get_static_int_field` for `android.R` ids looked up by a runtime name. Class names → `snake_case` of the simple name (`LinearLayout$LayoutParams` → `linear_layout_layout_params`); `String` / `CharSequence` parameters take an Odin `string` (those wrappers need a context), `byte[]` takes `[]u8`, objects are `jobject`; object returns are local refs the caller frees. `android_argb` (app_android.odin) packs a `Color` for the `int` colour parameters. `g_android.env` is refreshed in every JNI callback. `targetSdk` is 34 to avoid forced edge-to-edge (and `onBackPressed` still fires without `enableOnBackInvokedCallback`). `android_dp` converts dp to px from `DisplayMetrics.density` (read once). The JNI table indices in `jni.odin` follow `struct JNINativeInterface` in the NDK's `jni.h`; check any new one there.
- **Row / Column (`flex_*.odin`):** `Axis` values equal the native orientation enums on every platform, so backends cast them directly (Windows has no native layout and uses the value as the main-axis index). The cross axis always stretches; `flex` 0 hugs, `flex` > 0 shares the spare main-axis space.
  - macOS/iOS: stack view with Fill distribution (`NSStackViewDistributionFill` is 0, GravityAreas is -1; UIKit's Fill is also 0). Cross-axis stretch is alignment `Width` (7) for a vertical stack / `Height` (8) for a horizontal one; UIKit's default alignment is already Fill. Flex children get hugging priority 1, others 1000, and `flex_link_sizes` adds `NSLayoutConstraint` multipliers between the flex children so weights are exact. NSStackView children need `translatesAutoresizingMaskIntoConstraints = NO` set explicitly; UIStackView does it itself. `text_field_label` is autoreleased, so `_label_init` retains it and hands that +1 to the scope (`objc_own`); the stack retains its arranged subviews.

- **Canvas (`canvas_*.odin`):** `on_draw` gets a `Painter` valid only during the call; `canvas_redraw` invalidates. The link's `preferredFrameRateRange` (80–120, preferred 120) plus `CADisableMinimumFrameDurationOnPhone` in `ios/Info.plist` is what gets 120 Hz on a ProMotion phone: a bare `setNeedsDisplay` loop is committed at 60. The iOS layer also has `drawsAsynchronously`: UIKit records `drawRect:` into a display list and rasterizes it on the main thread after `on_draw` returned, which the Bench's draw time does not show (iPhone 12 mini, Mixed: 2.4 ms inside, 15.8 ms after, so frames were dropped at 60 Hz; 1.5 ms after with the flag, the rest off the main thread).

A download that lands after its page's scope died is dropped: `image_dispose` sets `Image_Fetch.h` to nil.
  - Loading: `bitmap_from_file` resolves a relative path against `assets/` next to the executable (`os.get_executable_directory`; inside the `.app` on iOS). The build tool copies `app/assets` there; Android packages it with `aapt2 -A` and reads it through `NvFetch.readAsset`. `bitmap_fetch` heap-allocates a `Fetch` (`runtime.heap_allocator()`, since the worker has its own context). On Windows and Linux, `fetch_thread.odin` starts a self-cleaning `core:thread` running the backend's blocking `_http_get`, then `_post_main`; on macOS / iOS, `fetch_darwin.odin` runs the same worker on a detached raw `posix.pthread_create`, because `core:thread`'s `thread_name_darwin.odin` links `System.framework`, which the iPhoneSimulator SDK does not have. On the UI thread, `fetch_notify` (bracketed) decodes, calls `on_load` and frees the request.
  - macOS / iOS (`cg.odin`): ImageIO (`CGImageSourceCreateWithData` over an `NSData`) gives a `CGImageRef`. `_draw_image` flips the CTM inside the rect, because `CGContextDrawImage` draws bottom-up in these top-left contexts. Downloads use `NSData dataWithContentsOfURL:` inside `NS.scoped_autoreleasepool()`, and come back through `dispatch_async_f(&_dispatch_main_q, ..)` from libSystem, with no blocks. On macOS the widget is a drawn, flipped `NVImageView` NSView subclass, since NSImageView has no aspect fill. On iOS it is a `UIImageView` subclass with `contentMode` and `clipsToBounds`. Both override `intrinsicContentSize` (`"{CGSize=dd}@:"`).
  - Android: `BitmapFactory.decodeByteArray` produces a global ref that is never `recycle()`d. `draw_image` calls `drawBitmap(.., RectF, fill Paint)`; the paint is set opaque first, because its alpha would fade the image. The widget is `nv.NvImageView`, whose `onMeasure` uses `setNaturalSize` (px), since ImageView ignores `setMaxWidth` without `adjustViewBounds`; the `ScaleType` comes via `image_view_scale_type_value_of`. `NvFetch.start` downloads on a Java thread and posts `nativeOnFetch(req, byte[])` to the main Looper. The byte[] JNI helpers are `jni_byte_array` (used by the generated wrappers) and `jni_bytes_clone`, and the manifest has `INTERNET`.
  - Linux: `gdk_texture_new_from_bytes` (GTK 4.6), then `gdk_texture_download` into a cairo ARGB32 surface, which is all the bitmap keeps. The widget is a `GtkDrawingArea` whose `content_width/height` is the natural size (GtkPicture can't be made smaller than its paintable). Downloads use libcurl easy (`curl_global_init` in `_run`, `NOSIGNAL`), with `g_idle_add` back to the UI thread.
  - Windows: `SHCreateMemStream` + `GdipCreateBitmapFromStream`. GDI+ keeps reading the stream, so it lives in `Bitmap.extra` until `_bitmap_free`. Drawing is `GdipDrawImageRect` with bicubic interpolation. The widget is an `NVImage` window painted like the canvas; `measure` returns `px(image_natural_size)`, and a new bitmap calls `flex_relayout_ancestors`. Downloads use WinINet (`InternetOpenUrlW`) and post `WM_NV_FETCHED` (`WM_APP + 2`) to the main window.
- **Navigation (`nav_*.odin`):** `g_nav: [dynamic]^Page_Handle` in `nv.odin` is the page stack (heap entries, so handles stay valid while the stack grows); `g_nav[0]` is the root page from `run` and the depth is `len(g_nav) - 1`. `run` and `push` make the handle (`nav_page_new`: clone the title, copy the actions), `push` appends it, builds the page (`nav_build`, which passes the handle to `build`) and calls `_nav_push`; a `push` from inside a `build` is queued in `g_nav_pending` and runs after that page is shown (`nav_flush_pending`), so pages stack in call order. `pop` removes the top entry, calls `_nav_pop(top, below)` (the native transition; `below` is already the top of `g_nav`; it returns false and the entry goes back when the platform refuses, which UIKit does mid-transition), then `nav_finish_pop`: `_nav_release` (hands the page's scope to the backend, which retires it once the tree is gone), `on_pop`, free the actions, the title and the handle (so `on_pop` is the last call the handle is valid for). `nav_system_pop` is the same without `_nav_pop`, for pops the platform already made. Backends never modify `g_nav`. Every backend has a `nav_update_chrome(e)` (Android: `android_chrome`) for the title, the back button and the actions, and `_nav_title_changed(h)` / `_nav_actions_changed(h)` for `page_set_title` / `page_set_actions` (separate, so a title change doesn't rebuild the action controls): the bar shows the top page only, so they act only when `h` is the top (iOS has a controller per page in `h.native` and updates any page). The setters skip the backend while `h.root` is nil: during `build` (because `_nav_push` follows) and after `_nav_release` (`nav_finish_pop` nils `root`, `native` and `scope` before `on_pop`); the Android relaunch path nils the root before rebuilding for the same reason. `pop` inside a `build` is ignored, since the top page is the one being built. `pop` shadows the builtin inside the package, hence `builtin.pop(&g_nav)`. Widget handles have no destroy of their own: they die with their page's scope (see Scopes). `pop` on the root page is a no-op (on Android the Back key then finishes the Activity).
  - **Page actions:** `Page.actions` (`[]Action`: title, `Icon`, `on_click`) are copied on `run` / `push` into `Page_Handle.actions` (`[dynamic]^Action_Handle`, freed in `nav_finish_pop`); `page_set_actions(h, ..)` replaces them. Every backend rebuilds the trailing controls from `e.actions` in its `nav_update_chrome` / `android_chrome`, so push and pop need nothing extra. `action_notify(h)` copies `on_click` / `user` out of the handle first: the callback may call `page_set_actions` or `pop`, which frees the handle. The backends find the handle from the control: the `tag` on Apple (one shared `nvAction:` IMP, `nav_action_clicked` in `appkit.odin`, restores `h.ctx`), the signal data on GTK, `GWLP_USERDATA` on Windows, menu item id = index + 1 on Android. Icons are per-backend `[Icon]` tables (`sf_symbol_names` in `appkit.odin`, `android_icon_names`, `gtk_icon_names`, `mdl2_glyphs`); an empty entry shows the title as text.
    - macOS: a second `NSTitlebarAccessoryViewController` (layout attribute Trailing, 6) with an `NSButton` per action (`buttonWithTitle:` / `buttonWithImage:` with an SF Symbol, textured rounded), recreated on every chrome update because AppKit sizes the accessory from its view's frame when it is added; the old container is retained + autoreleased before removal since the call may come from its own button's action. Both the back button and the actions target the one `NVNavTarget` (`g_macos.nav_target`, selectors `nvBack:` / `nvAction:`).
    - iOS: `UIBarButtonItem`s (`initWithTitle:` / `initWithImage:` with `systemImageNamed:`) on the controller's `navigationItem.rightBarButtonItems`, in **reverse** order because UIKit lays them out from the right; set in `page_controller_new`, which also stores the controller in `h.native` for `_nav_title_changed` / `_nav_actions_changed`. The old items array is retained + autoreleased before it is replaced. The target is `g_app.nav_target` (`NVNavTarget`, registered in `_run`).
    - Android: `onCreateOptionsMenu` → `nativeOnCreateMenu` adds `menu.add(0, i + 1, i, title)` items with `setShowAsAction(IF_ROOM)` and `setIcon(android.R.drawable.*)` (resource ids through `jni_get_static_int_field`, by runtime name); `onOptionsItemSelected` → `nativeOnAction(id)`. `android_chrome` (title, up arrow, menu; `android_show` is `setContentView` + `android_chrome`) calls `invalidateOptionsMenu`, which the framework defers, so the menu can be replaced from inside an item's own click.
    - Linux: `gtk_header_bar_pack_end` in **reverse** order (pack_end packs right to left). Each button is `g_object_ref_sink`ed and, on rebuild, removed from the header and unreffed from a `g_idle_add` callback: the rebuild often runs inside the button's own `clicked` emission.
    - Windows: `Button`s as children of the `NVNav` host (`g_windows.nav_actions`) with the handle in `GWLP_USERDATA`; icon buttons use `g_windows.icon_font` (Segoe MDL2 Assets at 4/3 of the message font, created only if `GetTextFaceW` confirms the face) and the glyph as caption. The bar now also shows on the root page when it has actions (`nav_bar_shown`); actions are right-aligned in `nav_layout`, icon buttons at least square. Old buttons are hidden and destroyed through `WM_NV_DESTROY`, like pages, after moving the focus off them; `nav_proc` only dispatches a `BN_CLICKED` whose sender is in `nav_actions`. `label_set_text` and `button_set_title` call `flex_relayout_ancestors` only when `measure` changed (the app may set text on every keystroke).
  - macOS: the pages are subviews of `g_macos.content`, a plain `NSView` that is the window's content view (so dialogs can sit above them), pinned by `layout_pin_page`: they fill it at priority 499, below the window size (500), so a page with no flex child ends short instead of shrinking the window; pages below the top are hidden. `g_macos` also keeps the window and the back button, a chevron `NSButton` (`imageWithSystemSymbolName:`, macOS 11+) in an `NSTitlebarAccessoryViewController` with layout attribute Leading (5), hidden on the root. `_nav_release` retires the scope at once (`_nav_pop` already removed the root); its disposers autorelease rather than release: when `pop` runs from the page's own button, `removeFromSuperview` already dropped the container's reference and the button's action is still on the stack.
  - iOS: each page is a `UIViewController` (`page_controller_new`: container pinned to the safe area, title) pushed on the `UINavigationController` in `g_app.nav`; the root goes into `initWithRootViewController:` directly. Each controller is an `NVPageController` whose `didMoveToParentViewController:` (`page_did_move`) is the one signal for pops: with `parent` nil (and no `parentViewController` left, which a cancelled swipe keeps), a page still in `g_nav` was popped by the back button or a swipe and goes through `nav_system_pop_page` (by identity, not by count: iOS 18+ queues a transition requested during another, so a push can sit above the popped page in `g_nav`), and a page `pop()` already removed only has its scope retired. There is no navigation delegate; `didShowViewController:` and the controller count are not used, since a queued push is not in `viewControllers` yet when the previous transition's `didShow` fires. `on_pop` for a gesture runs after the animation.
  - Android: `setContentView` + `setTitle` + `getActionBar().setDisplayHomeAsUpEnabled(depth > 0)` (`android_show`). Popped-under pages stay alive as global refs (`setContentView` removes the old content first, so a re-shown page has no stale parent); a popped page's refs go with its scope. `nativeOnBack` returns false on the root so `super.onBackPressed()` finishes the Activity. A second `onCreate` in the same process resets the stack to the root (`nav_system_pop` for each pushed page, then the root's global ref is dropped and it is rebuilt).
  - Linux: a `GtkHeaderBar` as the titlebar (client-side decorations; it shows the window title) with a `go-previous-symbolic` button packed at the start, and a `GtkStack` with the Slide_Left_Right transition holding the pages. The stack owns a page from `gtk_stack_add_child` to `gtk_stack_remove`. A page popped while the slide runs is queued in `g_linux.dying` and removed on `notify::transition-running`, because removing it at once cuts it out of the animation and would finalize a button inside its own `clicked` emission; its scope is retired right after the removal, since the sliding page still draws.
  - Windows: `g_windows.root` is an `NVNav` host that fills the main window (`layout_root`); its bar (a `Button` "← Back" and a `Static` title in the title font, `g_windows.nav_back` / `nav_title`) is shown only on pushed pages, height `title_h + 12dp`. Page roots are created under `parking` and `SetParent`ed into the host (only the root moves, so the list / input / button containers keep their cached parents); pages below the top are hidden. `_nav_release` posts `WM_NV_DESTROY` (`WM_APP + 1`, the scope in `wparam`, retired after `DestroyWindow`) so a page's own Back button finishes its `BN_CLICKED` before `DestroyWindow`; `_nav_pop` moves the focus to the main window first, and the Edit subclass removes itself on `WM_NCDESTROY`. The window caption follows the page title.
- **Linux GTK4:** `run` uses `GtkApplication` (no app id) and builds the root view in `activate`. The list is a `GtkListView` over a `GListModel` type registered at runtime with `g_type_register_static_simple`; the instance size comes from `g_type_query` and the `^List_Handle` sits right after the GObject fields. Model items are throwaway `GObject`s, because GTK only rebinds a row when its item object changes. Rows are recycled by the `GtkSignalListItemFactory` `setup`/`bind` signals. `GtkSingleSelection` autoselects row 0 at construction, so `_list_init` turns off `autoselect`, turns on `can-unselect` (without it the unselect is silently ignored) and unselects. `list_reload` emits `items-changed` with the previously reported count. `cells_created` starts around 200 because GtkListView pre-creates up to 200 row widgets for measuring, then recycles them. Under Hyprland, keys can be sent for testing with `hyprctl dispatch "hl.dsp.send_shortcut({mods='', key='Down', window='address:<addr>'})"`.
- **Windows (Win32):**
  - Layout only runs on `WM_SIZE`, so a content change that alters a natural size (`button_set_title`) calls `flex_relayout_ancestors`.
  - `_run` creates the main window hidden *before* building the root page, so every control can be created as a `WS_CHILD` of it (`g_windows.parking`). Row / Column re-parent their children afterwards. DPI awareness is PerMonitorV2, and `px` converts dp to px at the window's DPI. Fonts come from the DPI-scaled message font. On `WM_DPICHANGED` only the window rect follows: fonts and row heights keep their startup DPI.
  - The list is a `SysListView32` in virtual mode (`LVS_OWNERDATA`, report view, one column, no header, Explorer theme) inside an `NVList` container window. ListView caches its parent for `WM_NOTIFY` at creation, so it needs a parent that is never re-parented. `^List_Handle` reaches the container through `lpCreateParams` → `GWLP_USERDATA`.
  - Report view can't show two lines per row. `LVN_GETDISPINFOW` returns empty text, the theme paints hover and selection, and `NM_CUSTOMDRAW` draws the title and subtitle in `CDDS_ITEMPOSTPAINT`. The row height comes from a 1×h image list set as `LVSIL_SMALL`. `cells_created` stays 0.
  - `core:sys/windows` declares `NM_CUSTOMDRAW` as a `uintptr`, so `list_windows.odin` redeclares it as a `UINT`.
  - `windows/app.manifest` (embedded through `-resource:windows\app.rc`) enables Common Controls v6. Without it the controls are unthemed.
