# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
Experimental "native views" framework for Odin, targeting macOS, iOS, Android, Linux, Windows and the web. It follows the Kotlin/Native approach: no codegen and no JS bridge. Odin code calls AppKit/UIKit directly through Objective-C interop, Android views through JNI, GTK4 and Win32 through plain C bindings, and the DOM through a small hand-written JS import module (wasm; every widget is an HTML element laid out by CSS, see Web below). Widgets so far: a vertically scrolling list (NSTableView / UITableView / ListView / GtkListView / SysListView32), a text label (optionally a heading), a single-line text input (NSTextField / UITextField / EditText / GtkEntry / Edit), a push button (NSButton / UIButton / Button / GtkButton / Button), a custom-drawn canvas (NSView / UIView subclasses, a View subclass, GtkDrawingArea, a GDI+ window), an image loaded from bytes, a file or a URL (a drawn NSView subclass / a UIImageView subclass / an ImageView subclass / GtkDrawingArea / a GDI+ window; the canvas draws the same bitmaps), a Flutter-style circular progress indicator (drawn on a canvas in a fixed-size Container, determinate or spinning), Flutter-style Row / Column stacks (NSStackView / UIStackView / LinearLayout / GtkBox / a hand-written layout window on Windows), a Flutter-style Stack that layers its children by alignment and margins (an NSView / UIView with anchor constraints / a FrameLayout / a GtkOverlay / an NVOverlay window), a Flutter-style Container with margin, border, background, rounded corners, padding and an optional fixed size around one child (an NSView holding an NSBox / a UIView with a CALayer / an nv.NvContainerView FrameLayout with a GradientDrawable / a GtkBox styled by a per-widget CSS rule / an NVContainer window painted with GDI+), a push/pop page stack (UINavigationController / the ActionBar's up arrow and the Back key / a back button in the title bar on macOS and GTK, an in-window bar on Windows), per-page bar actions (right bar button items / options menu items / GtkHeaderBar buttons / a trailing titlebar accessory / buttons in the Windows bar), an in-view dialog, modal or not (a card over the page inside the window: NSBox / UIView / FrameLayout on the decor view / GtkOverlay child / a child window of the Windows host), a Flutter-style Scaffold under the page's bar (bottom tabs: NSSegmentedControl / UITabBar / a LinearLayout of items / grouped GtkToggleButtons / an owner-drawn window; a floating action button; SnackBars; a drawer behind a scrim, opened by a menu button in the root page's bar), and a theme: light / dark / system mode, an accent and default text styles, plus a per-widget `Text_Style` (size, weight, italic, color in the system font, or a custom font loaded from bytes or an asset file: CGFont+CTFont / Typeface / fontconfig / AddFontMemResourceEx). The layout is Flutter-style: one shared app, framework backends per OS, and per-OS host folders that only handle packaging.

## Commands
One build tool, `tools/nvbuild` (an Odin program, so Odin is the only prerequisite), replaces per-OS scripts:
`odin run tools/nvbuild -- [build|check|clean|test|ci] [--platform=windows|macos|ios|android|linux|web|all] [--release|--debug] [--no-run] [--sim="iPhone 17"] [--avd=Pixel_10] [--device=<serial>] [--team=<id>] [--port=8000] [--no-open] [--any-odin]`.
`build` (the default) compiles `app/` for the platform (this host when none is given), packages it and runs it with the console attached; `--release` is `-o:speed` instead of `-debug`, `--no-run` stops after packaging. `check` type-checks `nv` and `app` with `-vet -strict-style` for one target or, with `all`, every target (iOS as both the simulator and the device subtarget, the web as `js_wasm32`) plus `tools/nvbuild` and `android/jnigen` (the cross-target checks work from any host; the Android one only needs the `ODIN_ANDROID_*` variables to be set, which the tool does with placeholders when there is no SDK; off Windows, `odin check` refuses a Windows target without `-windows-sdk-root`, which only `build` takes, so the Windows check is an `odin build -build-mode:obj` against the empty `build/check/winsdk` into `build/check/`). `clean` removes `build/<platform>` or all of `build/`. Every spawned command is echoed with a leading `+`, and the first failing one ends the build with its exit code. `odin run` leaves the tool's binary (`nvbuild`, gitignored) in the cwd; the package is not called `build` because that name would collide with the output directory. Every command but `clean` first checks that the compiler that built the tool (`ODIN_VERSION_HASH`) and the `odin` on PATH are both the pinned one (`ODIN_PIN` in `tools/nvbuild/main.odin`, `dev-2026-11-nightly:9a69916`); `--any-odin` skips only the comparison with the pin (the two must still be one compiler; two built without a git hash cannot be told apart). The pin moves only on purpose: how the compiler links a shared library decides how `libapp.so` starts on Android.
- macOS: `build/macos/example`. Without the screen-recording permission `screencapture` fails; render the window in-process instead (`bitmapImageRepForCachingDisplayInRect:` + `cacheDisplayInRect:toBitmapImageRep:` on the frame view, as dewesoftm_odin's `shot_macos.odin` does).
- iOS simulator: `build/ios/NativeList.app` (Info.plist and assets inside, ad-hoc signed, installed on the `--sim` simulator, a name or a UDID, booted first and unambiguous when several are booted, and launched with a console attached). Screenshot the simulator: `xcrun simctl io booted screenshot build/ios/shot.png`
- iOS device (`--platform=ios --device=<name|udid>`, a paired physical device from `xcrun devicectl list devices`; never auto-detected, since paired devices also show up over Wi-Fi): `build/ios/device/NativeList.app`, built with `-subtarget:iphone`. `ios/Info.plist` is the simulator's, so the copy gets `iPhoneOS` as its supported platform, and the dSYM is moved out of the bundle. Signing needs no configuration (`ios_signing` in `tools/nvbuild/apple.odin`): it takes the first development provisioning profile in Xcode's profile directories that is not expired, covers the bundle id (an exact app id over a wildcard) and the device, and lists a certificate that `security find-identity` has as a valid identity; `--team=<id>` narrows it to one team. The profile is embedded, the entitlements (`application-identifier`, team, `get-task-allow`) are generated, and `codesign` gets the certificate's SHA-1 (names repeat in a keychain). Install and launch are `xcrun devicectl device install app` / `device process launch --console --terminate-existing` (the phone must be unlocked). With no fitting profile the build stops: Xcode has to create one (automatic signing on a project with the bundle id, run once on the device).
- Android (default AVD `Pixel_10`; the `Pixel_8a` image is incomplete): the SDK comes from `ANDROID_HOME` / `ANDROID_SDK_ROOT` or the host's default install location, the NDK and build-tools are the highest installed, the JDK from `JAVA_HOME` (else Homebrew's openjdk@21 on macOS, else PATH). It compiles the Java shims, regenerates the JNI wrappers (`android/jnigen`, needs `javap`), builds `libapp.so`, and packages it without Gradle (d8 → aapt2 → `jar` → zipalign → apksigner; d8 and apksigner are run through `java` since they are batch files on Windows, and the debug keystore is created with `keytool` when missing), installs and launches on `--device=<serial>` (from `adb devices`), else on the only attached device; with none it starts the `--avd` emulator and waits for `sys.boot_completed`, with several it stops and asks for `--device`; every adb call passes `-s`. App stdout goes to `adb -s <serial> logcat -s nv`. Screenshot with `adb exec-out screencap -p > build/android/shot.png`; `adb shell input tap/swipe` can drive the UI.
- Linux: `build/linux/example` against GTK4. Only the GTK4 and libcurl runtimes are required: without `libgtk-4-dev` / `libcurl-dev` the tool symlinks `libgtk-4.so.1` / `libcurl.so.4` (and the pango / fontconfig libraries) into `build/linux/libs` for the linker. Under Hyprland, screenshot with `grim -g "$(hyprctl clients -j | jq -r '.[] | select(.class=="example") | "\(.at[0]),\(.at[1]) \(.size[0])x\(.size[1])"')" build/linux/shot.png` (select by class: the title changes with the page).
- Windows: `build\windows\example.exe` with the manifest from `windows\app.rc` embedded. To screenshot, get the window rect from `(Get-Process example).MainWindowHandle` with `GetWindowRect` (after `SetProcessDPIAware`) and use `System.Drawing.Graphics.CopyFromScreen`.
- Web (`tools/nvbuild/web.odin`): `build/web/` holds `app.wasm` (`-target:js_wasm32`), `index.html` / `nv.js` / `nv.css` from `nv/web/`, the compiler's own `odin.js` (from `odin root`, so its runtime imports match the wasm), and `assets/` with `assets.json` (the list nv.js fetches before the app starts). Unless `--no-run`, nvbuild then serves `build/web` itself (a small `core:net` server, one thread per connection, on 127.0.0.1, `--port`, default 8000; Ctrl-C stops it) and opens the default browser (`xdg-open` / `open` / `start`; `--no-open` skips that, then reload the open tab: the server reads the files on every request, so a rebuild with `--no-run` is picked up by a reload). A debug build's page posts the app's stdout and uncaught JS errors to `POST /__nv/log`, which the server prints, so the console is attached like elsewhere; a release build (`--release`, about 320 KB of wasm) does not. A cross-origin `bitmap_fetch` needs CORS headers on the server it downloads from. Drive it headless with Chrome's DevTools protocol (`google-chrome --headless=new --remote-debugging-port=..`, then `Input.dispatchMouseEvent` / `Page.captureScreenshot`); `nv.liveElements()` in the console counts the element ids nv holds (it returns to the same number after a push and pop; a dialog's `content` stays with its page, as everywhere, what its `build` made goes with it).
- Tests: `test` runs `odin test nv -vet -strict-style -define:ODIN_TEST_THREADS=1 -define:ODIN_TEST_FAIL_ON_BAD_MEMORY=true -out:build/<host>/nv_test` (`nv_test.exe` on Windows; one thread, since the core is package globals; a leak or a bad free of what the core allocates with `context.allocator` fails its test, while the heap and the scopes' arenas are not tracked; on Linux plus the `-L build/linux/libs` flag of `build`). The tests (`nv/*_test.odin`) run the core against a mock backend, so they need no window; one test by hand: add `-define:ODIN_TEST_NAMES=nv.test_push_and_pop`. They only cover the core's side of the backend contract: every backend still needs its click-through on a device. `ci` is `check --platform=all`, then `test`: the safety net before a push, since there is no hosted CI; `tools/hooks/pre-push` runs it once a clone opts in with `git config core.hooksPath tools/hooks` (`git push --no-verify` skips it).
- Compiler pin: to move `ODIN_PIN`, install the candidate and pass `--any-odin` to every command, then (1) `check --platform=all` and `test` pass; (2) host canary: `mkdir -p build && odin build tools/nvbuild -build-mode:shared -out:build/libcanary.so && readelf -d build/libcanary.so | grep -E '\((INIT|FINI)\)'` lists both from `085af86da` on; (3) with the NDK, the Android build prints `libapp.so has DT_INIT`; (4) on a device, `adb logcat -s nv` shows no `no DT_INIT` line, and a Theme switch to Dark, rotation, and, after an nvbuild launch, Back on the root then the launcher icon (a later `onCreate` in the same process) behave as before; (5) build the desktops where available. Then set `ODIN_PIN` to the new `odin version` text.
- The example app's Scaffold action (root bar, Home icon) pushes the Scaffold demo (`app/scaffold_demo.odin`): three tabs, a FAB that counts and shows a SnackBar with Undo (two lines on every third tap), and a drawer opened from the Home tab's button (a pushed page has no menu button).
- The example app's Bench action (root bar) pushes a page that times the canvas draw path: each button repaints a fixed workload for 60 frames and prints the average ms inside `on_draw` and per frame.

The core calls `g_backend.x(..)`; a backend calls its own `_x` directly. The eight draw procs are not in it (the canvas hot path); the tests install a mock.
- `nv/*_macos.odin` (with `appkit_macos.odin`) and `nv/*_ios.odin` (with `uikit.odin`), plus the shared `appkit.odin` and `cg.odin`: the platform backends (`list_*`, `flex_*` for Row/Column, `label_*`, `input_*`, `button_*`, `canvas_*`, `image_*`, `nav_*`, `app_*`).

These subtarget tags are in the compiler (`src/parser.cpp`) but not in Odin's docs, so `check` covers macOS, the simulator and the device: a wrong selection fails as a redeclared or undeclared `_` proc. `IS_IOS` remains in `cg.odin` for two in-proc branches; the `Sys_Font` / `Sys_Color` aliases it uses live in the per-platform files (`UI_Font` / `UI_Color` in `uikit.odin`; `NS_Font` / `AK.Color` in `appkit_macos.odin`), since `cg.odin` is shared with iOS and `vendor:darwin/AppKit` only builds for macOS.

- `nv/*_android.odin` / `jni.odin` / `jni_api_android.odin` (generated, see Android JNI below): the Android backend (`#+build linux:android`). The Apple files carry `#+build darwin:default` (macOS) or `#+build darwin:ios`, the shared `appkit.odin`, `cg.odin` and `fetch_darwin.odin` `#+build darwin`.
- `nv/*_linux.odin` / `gtk.odin`: the Linux GTK4 backend (`#+build linux:default`). As on Darwin, a subtarget build tag picks the backend.
- `nv/*_web.odin` / `web.odin` (`#+build js`) plus `nv/web/` (`nv.js`, `nv.css`, `index.html`): the web backend (see Web below). Not `_js.odin`: Odin would read that suffix as the build tag itself. `core:os` is a compile-time panic on js, so the file-system asset reader is `asset_file.odin` (`#+build !js`), and `core:mem/virtual` cannot reserve there, so the scope arena is `scope_arena.odin` (virtual; `runtime.Arena` blocks from the app's allocator once `set_allocator` gave one) / `scope_arena_web.odin` (`runtime.Arena` over `nv_heap()` blocks). `imagesize.odin` (shared, tested) reads an image's size from its header. `svg_path.odin` (shared, tested) replays SVG path data through a `Svg_Sink` (moves, lines, cubics, closes; arcs as cubics) and holds Material's icon paths by `Icon` (`material_icon_paths`, the same set as `nv.js`); Android's icons and the Windows bar draw from it.
- `nv/*_windows.odin` / `win32.odin`: the Windows backend (`#+build windows`). Bindings come from `core:sys/windows`; `win32.odin` holds the shared state (`g_windows`), helpers (`wstr`, `px`, fonts) and the few missing declarations.
- `nv/android/java/nv/`: the generic Java embedder. `NvActivity` loads `libapp.so`, forwards the Back key and the ActionBar's up arrow to `nativeOnBack`, and its options menu to `nativeOnCreateMenu` / `nativeOnAction`; `NvListAdapter` forwards `BaseAdapter` and click callbacks, and `NvInputListener` forwards `TextWatcher` / `OnEditorActionListener`, `NvClickListener` forwards `View.OnClickListener`, and `NvCanvasView` forwards `onDraw` / `onTouchEvent`, to exported `Java_nv_*` procs. `NvBarView` is the ActionBar's custom view (`android_title_install`): the page's leading view in a holder, then `NvTitleView`, the page title in `Theme.bar_title` (else `heading`) over the ActionBar title's own look, centred over the whole bar like a centred Flutter AppBar title and moved aside only as far as the sides need. `NvLayoutView` reports a Layout's size before it draws, and `NvFiles` runs the document picker (`NvActivity.onActivityResult` forwards to it). Java is only used where Android requires a subclass.
- `ios/`, `android/`, `windows/`: host packaging files only (`Info.plist`, `AndroidManifest.xml`, `app.rc` + `app.manifest`); `tools/nvbuild/` is the build tool (see Commands) and `android/jnigen/` the JNI wrapper generator.

## Backend patterns
- **Delegate classes:** ObjC classes are registered at runtime through `objc_class(&cache, name, super, methods, protocols)` in `appkit.odin` (shared by both Apple backends; `objc_allocateClassPair` + `class_addMethod` + `objc_registerClassPair` once, `cache` is the file's `X_class` global), with `Objc_Method{sel, imp, types}` entries: `proc "c"` IMPs passed through `auto_cast` and arm64 type encodings (for example `"q@:@"`).
  - `objc_alloc_with_handle(cls, h)` is `class_createInstance` with the handle pointer in the indexed ivars (a view subclass still needs its `initWithFrame:`), and `objc_handle(self, X_Handle)` reads it back in an IMP, which then restores `context = h.ctx` before calling Odin code. The app-level singletons (`NVNavTarget`, the iOS app / scene delegates) have no ivars and use `g_app.ctx` / `g_macos.ctx`.
- **App builder:** `run` takes a `build` proc because UIKit views can't exist before `UIApplicationMain`. `run` appends the root page to `g_nav` and calls `g_backend.run()` (`_run`), which takes no arguments: each backend calls `theme_start()` and `nav_show_root()` (bracketed) once views can exist (Android: from the first `onCreate`, after `run` returned). iOS instead builds the root itself (`nav_build`, then `nav_flush_pending`), since `UINavigationController` takes its root controller up front, so the root never reaches `_nav_push`.
  - On iOS the root view sits in a plain container view pinned to its `safeAreaLayoutGuide`, since a stack view would slide under the navigation bar.
  - iOS uses the UIScene lifecycle. `NVSceneDelegate` is named in `ios/Info.plist`, and the names must match `app_ios.odin`.
  - Scene and app delegates are created by UIKit, so they use package globals (`g_app`) instead of ivars.
- **Row height:** on iOS rows are self-sizing and `item_height` is only an estimate. At a fixed 44pt, UIKit's subtitle configuration hides the secondary text.
- **Strings:** use `ns_string`, which copies and autoreleases. `initWithOdinString` does not copy.
- **`post_main(fn, user)`:** the only nv proc callable from another thread. It heap-allocates a `Timer` with the context `run` stored in `g_main_ctx` (never the poster's: its temp allocator is thread-local) and hands it to the backend's thread-safe `post_timer`: `g_idle_add` (Linux), `dispatch_async_f` on the main queue (Apple), `PostMessageW(parking, WM_NV_POSTED)` (Windows), `setTimeout(0)` (web, single-threaded), a pipe watched by the UI thread's `ALooper` (Android: `post_start` in `_run`, no JNI). On the main thread `timer_fire` runs `fn` bracketed. The mock parks it with the timers (`mock_fire_timers`); `post_test.odin` posts from a `core:thread` worker.
- **Temp memory:** only `callback_exit` (`nv.odin`) calls `free_all(context.temp_allocator)`, when the outermost callback returns. Every entry from the platform that allocates or calls the app (`build`, row/select callbacks, `input_notify`, `button_notify`, `on_pop`, `on_close`, the back button / key handlers that call `pop`, the Win32 flex / nav / dialog `WM_SIZE`) is bracketed by `callback_enter()` / `defer callback_exit()`. `push`, `pop`, `dialog_show` and `dialog_close` themselves are app-called and don't bracket. Callbacks nest (an `on_click` that calls `input_set_text`, `list_reload` or `push`, a Win32 layout re-entering nested Row / Column procs), so an inner free would wipe the outer caller's strings. Procs the app calls never free.
- **Scopes (`scope.odin`):** every page (`Page_Handle.scope`, from `nav_page_new`) and every shown dialog body (`Dialog_Handle.scope`, from `dialog_present`, which sets `g_scope_override` while it builds the title / buttons / Row / Column) owns a `Scope`: a growing arena (`Scope_Arena`: `core:mem/virtual`, or heap blocks on the web) plus a LIFO list of disposers. `*_create` allocates its handle with `scope_new_in(T)` in `scope_current()` (the override, else the top of `g_nav`, which is the page being built during `build`), so widgets made in `build`, in a callback, or for a dialog's `content` belong to the top page. `context.allocator` is never replaced, so the app's allocations and `h.ctx` are untouched. Disposers (`scope_on_dispose(fn, data)`) release what a handle holds outside the arena: the heap label text / button title (`nv_heap()`, since the setters reallocate; `nv_heap` in `scope.odin` is the app's allocator once `set_allocator` gave one before `run` (it must be thread-safe: downloads and `post_main` allocate off the main thread; `test_set_allocator`), else `runtime.heap_allocator()`, or the wasm allocator on js, where `base:runtime` has no `heap_alloc`: everything that outlives a callback uses it, the backends' download buffers and macOS redraw tokens included), `font_free` / `bitmap_free`, and the backend's native references. The rule is that whoever creates a native reference registers its release; parents keep only their own retains (`addSubview`, `addView`, GTK parenting), so a page root is no longer released specially. Apple: `objc_own(obj)` (`appkit.odin`, shared) autoreleases the creator's +1 (autorelease, since the pop may run inside the object's own action), and `objc_clear_delegate_on_dispose` / `objc_clear_data_source_on_dispose` nil the weak slots. Android: `android_own_ref(env, obj)` (`app_android.odin`) is a global ref that the scope deletes. Linux: the container's CSS provider is removed from the display and unreffed. Windows: `Flex_Data` lives in the arena. The backend calls `scope_retire(s)` once the tree is really gone: macOS / Android in `_nav_release` / `_dialog_close`; iOS in the page controller's `didMoveToParentViewController:nil` (`page_did_move`), which UIKit sends once the popped controller has really left, after its transition and after any transition queued behind it: a programmatic `pop` parks the scope in `g_app.retiring` (with the retained controller) until then, a back button or swipe retires it from inside that call (`g_app.removing`); Linux right after `gtk_stack_remove` (`g_linux.dying` keeps `Linux_Dying{root, scope}`), and for a dialog from an idle queued after the card's unref; Windows in `WM_NV_DESTROY` after `DestroyWindow` (the scope rides in `wparam`; its `WM_NCDESTROY`s still read the handles). Inside a callback, `scope_retire` only queues: the outermost `callback_exit` destroys the queued scopes (`scope_flush_retired`) before freeing the temp allocator. So handles stay valid through `on_pop` / `on_close` and until the callback that popped returns. But the app frees its own data in `on_pop` / `on_close`, so the scope is *detached* first (`Scope.detached`, set in `nav_finish_pop` before `_nav_release` and in `dialog_close` before `_dialog_close`): from then on `scope_live(h.scope)` is false and the core delivers none of its widgets' callbacks while the platform still shows them (GTK's and iOS's slide, a queued layout): `button_notify`, `input_notify`, the canvas notifies (a sliding canvas keeps what it last drew), `fab_notify`, `tabbar_notify`, and lists, which the backends ask only through `list_count` (the last count, once detached), `list_item` (empty rows) and `list_select`. A handle whose type has a `scope` field gets it from `scope_new_in`; a new widget that calls the app needs one and a check in its notify (`test_popped_page_calls_nothing`, `test_closed_dialog_calls_nothing`). An image's download (`Image_Fetch`, on the heap) is detached by `image_dispose` (`fetch.h = nil`), and so is a canvas's queued redraw on macOS (`Apple_Canvas_Redraw`, by `apple_canvas_dispose`, which on iOS invalidates the canvas's display link).
- **`objc_send` arguments:** literals must be typed (`NS.BOOL(true)`, `NS.Integer(0)`), and nil object arguments are passed as `NS.id(nil)`.
- **Android startup:** the runtime's `_odin_entry_point` runs the `@init` procedures (without them `os.stdout` is nil and fmt prints nothing); it should be `libapp.so`'s DT_INIT, run by `System.loadLibrary` in `NvActivity`'s static initializer. Odin before `085af86da` (dev-2026-09 included) spawns the linker without a shell, so `-Wl,-init,'_odin_entry_point'` reaches LLD with its quotes and DT_INIT is silently left out (desktop shared libraries lose it too; it is not an Android trait). Both cases work: the `@(init)` proc `android_runtime_started` sets `g_android.started`, and the first `jni_on_create` that finds it unset runs the entry through `dlsym`. Since dev-2026-11 the Android entry point no longer calls the app's `main` (`core:sys/android/native_app_glue` does, for a NativeActivity, on a thread of its own), and the compiler rejects a `main` on Android that nothing calls: the first `jni_on_create` runs it once (`g_android.main_ran`) through `intrinsics.__entry_point()`, as the glue does, on the UI thread, after it stored the env and the Activity; that call is also what satisfies the check. So `main` can load the theme's fonts (an APK asset, a Typeface); `run` returns at once (`_run` keeps `g_android.ctx` and starts `post_main`'s pipe; stdout goes to logcat from before `main`), and before `run` the app calls only `set_allocator`, `theme_set` / `theme_set_mode` and the font loaders (`theme_dark` / `theme_palette` answer light with no system accent). The first `onCreate` runs `theme_start` and `set_content`; a later one in the same process (`g_android.shown`: a night-mode or other configuration recreation, or a launch after Back on the root finished the Activity while the process lived; on API 34+ Back on the root finishes it after nvbuild's `am start -n` and any other explicit launch, and only moves the task to the back when the launcher started it with a MAIN / LAUNCHER intent) swaps the Activity global ref, resets the stack to the root, calls `theme_notify` and builds the root page again, so `build` runs once per Activity. The Android build prints whether `libapp.so` has DT_INIT. The `main` link name is reserved. `android:configChanges` in the manifest keeps rotation from recreating the Activity.

- **Android JNI:** every Java member is called through a typed wrapper in `nv/jni_api_android.odin` (`view_set_padding(env, v, l, t, r, b)`, `text_view_set_text(env, v, text)`, `paint_style_value_of(env, "STROKE")`, ..), **generated** by `android/jnigen` (an Odin program the build tool runs before `odin build`) from `nv/android/jni_api.txt`: one `class member` line per member in Java syntax (`<init>(..)` for constructors, `.field` for fields, an optional return type to disambiguate overloads, `= name` to override the Odin name), with every descriptor taken from `javap -s` over `android.jar` plus the compiled `nv/*` shims, so a misspelled or missing member fails the build instead of crashing the app. The generated file is committed (so `odin check` works without the SDK); to call a new member add its line and rebuild (or run the generator by hand, see its header). No descriptor is written by hand: `jni.odin` only has `jni_new_object` / `jni_call_*` / `jni_get_*_field` over a `Jni_Method` / `Jni_Field` (class global ref and ID resolved once, on first use; the wrapper names the *declaring* class, whose method ID works on subclass instances), the ref / string / byte[] helpers, and `jni_get_static_int_field` for `android.R` ids looked up by a runtime name. Class names → `snake_case` of the simple name (`LinearLayout$LayoutParams` → `linear_layout_layout_params`); `String` / `CharSequence` parameters take an Odin `string` (those wrappers need a context), `byte[]` takes `[]u8`, objects are `jobject`; object returns are local refs the caller frees. `android_argb` (app_android.odin) packs a `Color` for the `int` colour parameters. `g_android.env` is refreshed in every JNI callback. `targetSdk` is 34 to avoid forced edge-to-edge (and `onBackPressed` still fires without `enableOnBackInvokedCallback`). `android_dp` converts dp to px from `DisplayMetrics.density` (read once). The JNI table indices in `jni.odin` follow `struct JNINativeInterface` in the NDK's `jni.h`; check any new one there.
- **Row / Column (`flex_*.odin`):** `Axis` values equal the native orientation enums on every platform, so backends cast them directly (Windows has no native layout and uses the value as the main-axis index). The cross axis always stretches; `flex` 0 hugs, `flex` > 0 shares the spare main-axis space.
  - macOS/iOS: stack view with Fill distribution (`NSStackViewDistributionFill` is 0, GravityAreas is -1; UIKit's Fill is also 0). Cross-axis stretch is alignment `Width` (7) for a vertical stack / `Height` (8) for a horizontal one; UIKit's default alignment is already Fill. Flex children get hugging priority 1, others 1000, and `flex_link_sizes` adds `NSLayoutConstraint` multipliers between the flex children so weights are exact. NSStackView children need `translatesAutoresizingMaskIntoConstraints = NO` set explicitly; UIStackView does it itself. `text_field_label` is autoreleased, so `_label_init` retains it and hands that +1 to the scope (`objc_own`); the stack retains its arranged subviews. Every child also gets hugging 1 on the cross axis (forwarded through `container_forward_hugging`): the stack's Width / Height alignment ranks below a view's default hugging (250), so without it a label or a fixed-size container keeps its natural width and drifts to the trailing edge.
  - Android: `LinearLayout` with `LinearLayout.LayoutParams(w, h, weight)`; a flex child has main-axis size 0 and `weight = flex`, a flex-0 child is `WRAP_CONTENT`, the cross axis is `MATCH_PARENT`. Spacing is a top/left margin (`setMargins`) in px on every child after the first. `setTypeface(null, BOLD)` is how a bold label goes bold without looking up `Typeface.DEFAULT_BOLD`.
  - Windows: an `NVFlex` window with a `Flex_Data` in `GWLP_USERDATA` lays out its children on `WM_SIZE`. Flex-0 children get their `measure` size (text extent in its own font for a `Static` label, stacked children for a nested flex, 0 otherwise), and the flex children split the spare space by cumulative weight, so the rounding error never adds up. `_flex_create` re-parents children with `SetParent`. `label_new(text, parent, style, font)` makes a Static (`g_windows.title` for a bold label and the bar title, `g_windows.font` otherwise).
- **Container (`container_*.odin`):** `Container` is Flutter's: `margin` (outside), a `border_width` border in `border_color` and the `color` background, both rounded by `radius`, `padding`, then `child` filling the rest; `width` / `height` are the natural size including padding and border but not the margin (0 = from the child), the cross axis of a Row / Column still stretches and a flex > 0 child ignores them on the main axis, like Image. `Insets` is per side (`insets_all`, `insets_symmetric`). The root view is the **margin box** on every platform (Flutter puts the margin inside the box it hands to its parent, and the Android LinearLayout / Windows flex would otherwise have to know about margins); `container_frame(h)` (nv.odin) is the child's inset per side. The only setter is `container_set_color`. `color_argb` (nv.odin, shared) packs a `Color` for Android / GDI+; `android_argb` wraps it for JNI.
  - `container_set_size(h, w, h)` replaces `width` / `height` (0 = from the child): Apple sets the compression resistance per axis (751 fixed, 750 free), drops the child's hugging to 250 on a fixed axis or forwards the root's again on a free one, then `invalidateIntrinsicContentSize`; Android `setNaturalSize`; GTK `set_size_request`; the web toggles `nv-fw` / `nv-fh` and `--nv-w` / `--nv-h`; Windows relays out the ancestors (`flex_relayout_ancestors`), since `container_measure` reads the fields.
- **Layout (`layout_*.odin`, `layout_test.odin`):** Flutter's LayoutBuilder: `layout_create(Layout{child, on_layout, user})`, `layout_view` in the `view` group, `layout_size`. The child fills it and it takes the size its parent gives it; `layout_notify` (core) calls `on_layout(width, height)` only for a real change and never for 0 × 0 (hidden / not laid out), brackets it, and turns a size reported again from inside the answer (Windows' synchronous relayout) into one more pass after it, at most `LAYOUT_MAX_PASSES`. The app answers with `view_set_hidden` / `container_set_size`.
  - macOS / iOS: `NVLayoutView` overrides `layout` (macOS, plus `setFrameSize:` asking for a layout pass on a size change) / `layoutSubviews` (iOS) and reports `bounds` before `[super …]` (`objc_send_super` in `appkit.odin`, a typed cast of `objc_msgSendSuper`), so the answer is solved in the same pass. `layout_pin_child` pins top / leading required and trailing / bottom at `LAYOUT_PRIORITY_CHILD` (100, below a stack's cross-axis fill, the page's 499 and the window's), and the child's hugging drops to 1: the child never sizes the Layout (a fixed-width child would otherwise hold the page and the window). `container_forward_hugging` passes through a Layout (`layout_forward_hugging`).
  - Android: `nv.NvLayoutView` (FrameLayout + `OnPreDrawListener`): a new size calls `nativeOnLayout` (px → dp) and cancels that frame, so the traversal the answer asks for draws first.
  - Linux: a `GtkBox` with a `GtkCustomLayout` (`gtk_custom_layout_new`, `gtk_widget_set_layout_manager`): measure asks no minimum of its own (the window can shrink), allocate notifies, re-measures the child and allocates it (at least its minimum; `overflow` hidden).
  - Web: `div.nv-layout` observed by `layoutObserver`, created before the canvases' `resizeObserver` so the answer is in the DOM before they measure; export `nv_web_layout`.
  - Windows: an `NVLayout` window: `WM_SIZE` notifies, then sizes the child; `measure` returns the child's.
  - macOS / iOS: the root is a runtime `NVContainerView` NSView / UIView subclass whose only override is `intrinsicContentSize` (`container_intrinsic`: the fixed size + margin, or -1 = no metric per axis); a fixed axis also gets compression resistance `LAYOUT_PRIORITY_FIXED` (751: above a child's 750, below the stack's required stretch, which must win or Auto Layout reports a conflict). Inside it a custom `NSBox` (`box_new`, `box_set_fill_color`, `box_set_corner_radius`, `box_set_border`) / a `UIView` (`ui_view_set_corner_radius`, `ui_view_set_layer_border`, `ui_view_set_masks_to_bounds`) is pinned by the margin with `layout_pin_insets` (`appkit.odin`, shared; `layout_dialog_card` uses it too), and the child (added to `box_content_view` on macOS) is pinned to the **box's** anchors by padding + border width, since the border draws inside the bounds. NSBox does not clip the child to the corners; the iOS layer does. `flex_*` calls `container_forward_hugging`: the stack's hugging priority lands on the root, but stretching is decided against the child's own (a label's 250), so it is passed down to the child, except on a fixed axis, where a required hugging on the child would conflict with the root's intrinsic size.
  - Android: `nv.NvContainerView` (a FrameLayout with `setNaturalSize(px)`, whose `onMeasure` forces a fixed axis with an EXACTLY spec after `resolveSize`, so a parent's EXACTLY spec still wins). `flex_android.odin` replaces a child's LayoutParams, so the margin is view padding (margin + border + padding per side) and the background is the `GradientDrawable` (`setColor`, `setCornerRadius`, `setStroke`) inside an `InsetDrawable` with the margin as insets. The drawable's global ref is `h.box`; the child gets MATCH_PARENT × MATCH_PARENT params.
  - Linux: a `GtkBox` with the GTK margin properties, `gtk_widget_set_size_request` (a **minimum**: a larger child grows the container) and `gtk_widget_set_overflow(.Hidden)`; explicit `hexpand` / `vexpand` false on the box, true on the child. GTK4 has no background API, so each container gets a unique class `nv-c<N>` and its own `GtkCssProvider` on the display (the per-widget provider API is deprecated), holding one rule with background, border, radius and padding (`container_load_css`; `fmt` needs `{{` / `}}` for literal braces); `_container_set_color` reloads it. `Linux_Container` in `h.box` (in the scope's arena) keeps the provider and the number; `container_dispose` removes the provider from the display.

- **Label (`label_*.odin`):** `Label.heading` is the heading style (bold 17pt / 20sp bold / GTK `title-4` / the Windows title font); plain is the system body font (15pt on macOS, 17pt on iOS, 16sp, a bare GtkLabel, the message font). `Label.style` goes over it; with a loaded `style.font`, `heading` only keeps the heading size. - **Font (`font_*.odin`, `opentype.odin`, `cg.odin` on Apple):** `Font` is reference counted like `Bitmap` (`font_retain` on `h.x.style.font` in `*_create`, `font_free` in the scope disposer); `font_from_bytes` first runs `opentype_info` (shared, no build tag: family from the `name` table nameID 1, which GDI matches, plus `usWeightClass` / italic from `OS/2`), then `_font_load(f, data)`. Nothing unregisters one app font, and a system fontconfig reload drops them. The build tool symlinks pango / pangocairo / pangoft2 / fontconfig like gtk-4.

The draw path is immediate: every primitive is one native call and a redraw repaints the whole view, so per-call state that would otherwise be recreated (paints, pens, fonts, text attributes, the back buffer) lives in a per-backend struct in `Canvas_Handle.extra` (`Android_Canvas` / `Apple_Canvas` / `Linux_Canvas` / `Windows_Canvas`, in the page's arena, with a scope disposer for the native objects). `stroke_polyline(p, points, color, width)` is one stroked path (round joins, butt ends; under two points nothing), `clip_push(p, x, y, w, h)` / `clip_pop(p)` a nested rectangular clip (save the drawing state, clip; restore). The core counts them in `Painter.clips`: a pop without a push does nothing and `canvas_draw_notify` pops what `on_draw` left pushed, so the backends' save / restore always balance. A restore reverts the context's colour / width / font on CG, cairo and the 2D canvas, so their skip-repeated-state caches are reset on pop. The draw procs bypass `g_backend`, so the tests log these three through `g_draw_mock` (set by the mock, nil in an app; `test_polyline_and_clips`).

The macOS one is flipped and takes `mouseDown/Dragged/Up:`; iOS takes `touches*:withEvent:` and sets content mode Redraw. Pixels are offset by half (`PixelOffsetModeHalf`, as in `image_paint`): pixel i covers [i, i+1] as in CoreGraphics, cairo and Skia, and `_fill_rect` rounds its edges to whole pixels (a side under a pixel keeps its fractional edges), so fills that meet (a card drawn in pieces, stacked rows) leave no anti-aliased seam. - **Image (`image_*.odin`, `fetch_thread.odin` / `fetch_darwin.odin`):** a `Bitmap` is a decoded image with a reference count: `bitmap_free` drops a reference, and `image_create` / `image_set_bitmap` take one, so the app can free right after handing a bitmap over. `Image` shows `bitmap`, or else fetches `url` itself. `seq` drops a download that lost the race to a later `image_set_bitmap`. - **Navigation (`nav_*.odin`):** `g_nav: [dynamic]^Page_Handle` in `nv.odin` is the page stack (heap entries, so handles stay valid while the stack grows); `g_nav[0]` is the root page from `run` and the depth is `len(g_nav) - 1`. `run` and `push` make the handle (`nav_page_new`: clone the title, copy the actions), `push` appends it, builds the page (`nav_build`, which passes the handle to `build`) and calls `_nav_push`; a `push` from inside a `build` is queued in `g_nav_pending` and runs after that page is shown (`nav_flush_pending`), so pages stack in call order. `pop` removes the top entry, calls `_nav_pop(top, below)` (the native transition; `below` is already the top of `g_nav`; it returns false and the entry goes back when the platform refuses, which UIKit does mid-transition; the refused page is kept in `g_nav_pop_waiting`, and `nav_transition_done`, which the backend calls when a transition finished (iOS: the navigation controller's delegate, `NVNavTarget`'s `navigationController:didShowViewController:animated:` → `nav_did_show`), pops it if it is still the top; `nav_finish_pop` drops it when the page goes another way), then `nav_finish_pop`: `_nav_release` (hands the page's scope to the backend, which retires it once the tree is gone), `on_pop`, free the actions, the title and the handle (so `on_pop` is the last call the handle is valid for). `nav_system_pop` is the same without `_nav_pop`, for pops the platform already made. The buttons' window text is always the title ("Back", "Menu", the action's), which screen readers read. The bar's buttons (back, the drawer's menu, the actions) are `BS_OWNERDRAW`, painted by `nav_draw_button` on `WM_DRAWITEM` like an AppBar's IconButtons: Material's icon at 24dp (`material_icon_paths` and `MATERIAL_BACK_PATH` in `svg_path.odin`, replayed onto a GDI+ path filled with the winding rule) or the title when the icon has no path, square for an icon, with a translucent circle (a pill for text) while pressed or keyboard-focused. Page roots are created under `parking` and `SetParent`ed into the host (only the root moves, so the list / input / button containers keep their cached parents); pages below the top are hidden. `_nav_release` posts `WM_NV_DESTROY` (`WM_APP + 1`, the scope in `wparam`, retired after `DestroyWindow`) so a page's own Back button finishes its `BN_CLICKED` before `DestroyWindow`; `_nav_pop` moves the focus to the main window first, and the Edit subclass removes itself on `WM_NCDESTROY`. The window caption follows the page title.
- **Web (`*_web.odin`, `nv/web/`):** the DOM is the toolkit. `web.odin` has the `foreign import nv_js "nv"` block (contextless `js_*` procs: strings and slices arrive in JS as pointer + length, read with odin.js's `WasmMemoryInterface`; the names are the keys of `imports` in `nv.js`, so a missing one fails `WebAssembly.instantiate`), `g_web` (the bar's elements and the page host) and the exports nv.js calls back (`nv_web_event(kind, h, arg)` for clicks / edits / Back / theme with `Web_Event` = `EV` in nv.js, `nv_web_list_bind`, `nv_web_draw`, `nv_web_pointer`, `nv_web_alloc` + `nv_web_fetched`, `nv_web_timer`, `nv_web_depth`), each restoring the context and bracketed. `wasm-objdump -x -j Import build/web/app.wasm` lists what the wasm wants. An app adds its own import modules with `nv.start({..., imports: (env) => ({app: {...}})})`: `env.mem` is the WasmMemoryInterface and `env.exports()` the instance's exports once instantiated (for the app's `@(export)` callbacks); nv's own `nv` module can't be replaced.
  - Elements: a `View` is an id into nv.js's `els` table (never 0). `web_create(tag, class)` makes one owned by the current scope (its disposer `js_release`s it, which also removes it from the document); elements the backends keep (the bar, a page's `.nv-page` in `Page_Handle.native`, a dialog's card and scrim) are `js_create`d and released by hand. A label is `js_label` (a flex box centering a span, whose text `js_text` sets, cut with an ellipsis).
  - Startup: `nv.start` (index.html) fetches `assets.json` and every asset, instantiates with odin.js's `setupDefaultImports` plus `nv`, and calls `_start` but never `_end` (odin.js's own `runWasm` calls `_end` when there is no `step` export, which would run the fini procs). `main` → `run` → `_run` builds the bar and the root page at once and returns, like Android. `_asset_read` copies from the prefetched map (relative paths only).
  - Layout is CSS (`nv.css`): Row / Column are `.nv-row` / `.nv-col` flexboxes (`gap` = spacing; flex > 0 is `flex: N 1 0px` + `.nv-grow`, so weights are exact; flex 0 is `flex: none`; a hidden child drops out with its gap). A fixed natural size (Container, Image) is `--nv-w` / `--nv-h` with the `.nv-fw` / `.nv-fh` classes, which a parent `.nv-col` / `.nv-row` (and a Fill overlay axis, inline `width: auto`) turns into a minimum so the cross axis still stretches. Container: `.nv-container` (padding = margin) around `.nv-box` (border, radius, background, padding, `overflow: hidden`). List, canvas and image views have no natural size: their content is absolutely positioned. Overlay (Stack, Scaffold): `.nv-overlay` is a one-cell grid (`minmax(0, 1fr)`) where `sizes` children sit by `justify-self` / `align-self` + margins and the others are `.nv-abs` layers placed by `left` / `right` / `top` / `bottom` (+ `translate(-50%)` when centered); every child is positioned, so the DOM order is the paint order. Hidden is `.nv-hidden` (`display: none`), disabled is `inert`.
  - Navigation: `#nv-app` = `.nv-bar` (back button, menu button, title, `.nv-bar-actions`) over `.nv-pages`; each page is an `.nv-page` (absolutely filling the host, the root `flex: 1`), the pages below are `.nv-below` (`content-visibility: hidden`, which keeps their scroll positions). `document.title` follows the title. History: `nav_update_chrome` calls `js_history(depth)` and nv.js keeps one entry per depth (`{nv: depth}`; pushes `pushState`, an app pop `history.go(-n)` whose popstate it swallows); a user Back (popstate) runs `nav_back_notify` once per entry left behind, then re-syncs, so a Back that pops nothing (modal dialog, open drawer) puts the entry back, and Forward is undone. Back on the root leaves the page, like Android finishing.
  - List: a virtualized scroller (`js_list_create`, `js_list_count` on init and reload): a spacer of `count × item_height` and absolutely placed `.nv-cell` rows for the visible range (± 2), recycled through a pool; each newly shown row calls `nv_web_list_bind` (`fresh` counts `cells_created` and applies the row styles). A click selects (`.nv-selected`) and reports `on_select`.
  - Canvas: `<canvas>` absolutely filling `.nv-canvas`, sized by a `ResizeObserver` at `devicePixelRatio` (drawn at once on a resize). `_canvas_redraw` coalesces into one `requestAnimationFrame`, so a redraw from inside `on_draw` animates at the display rate (Bench, Progress); a canvas that is not shown (`checkVisibility()`: a page below, a hidden tab) is marked stale and drawn when it shows (`js_hidden(.., false)`, `js_show_page`). The draw procs paint on nv.js's current context (`Painter.native` is unused) and skip a repeated colour / width / font; colors cross as `color_argb`; text is placed at `y + fontBoundingBoxAscent`, cached per font string; lines have round caps, arcs and rects butt.
  - Bitmaps / fonts: the browser only decodes asynchronously, so `_bitmap_decode` takes the size from `image_size` (PNG, JPEG, GIF, WebP, BMP headers; anything else is not an image here) and nv.js keeps a Blob: `createImageBitmap` for `draw_image` (every canvas redraws once a decode lands; before that it draws nothing), a blob URL for the Image widget's `<img>` (`object-fit` from `Fit`). A Font is a `FontFace` named `nv-font-<id>` (`Font.native`) with the face's weight / style descriptors, in `document.fonts`; widgets use `font-family: "nv-font-<id>", var(--nv-font)` and reflow when it loads, canvases redraw. Downloads are `fetch()` (CORS applies).
  - Dialog: `.nv-dscrim` + `.nv-dialog` card (centered, `min(320px, 100% - 32px)`) appended to `#nv-app`, so the scrim covers the bar too; the scrim's click is `Web_Event.Dialog_Scrim` (`EV.DIALOG_SCRIM`, 11) with the scrim's id as `h`; `web_apply_modal` makes the bar, the pages and every other dialog `inert` while the top page has a visible modal dialog, and the first button takes the focus.
  - Scaffold: FAB `.nv-fab` (`.nv-round` without a title; no-icon round shows Add), tab bar `.nv-tabbar` of `.nv-tab` buttons (repainted before `tabbar_notify`), scrim `.nv-scrim.nv-abs` with a click, menu button in the bar per `nav_shows_menu`, `_post_delayed` = `setTimeout` → `nv_web_timer`.
  - Theme: `web_theme_vars(dark)` writes the palette as `--nv-bg` / `--nv-surface` / `--nv-text` / `--nv-text2` / `--nv-sep` / `--nv-accent` on `:root` plus `color-scheme` (native controls, scroll bars); System is `matchMedia('(prefers-color-scheme: dark)')`, whose `change` arrives as `Web_Event.Theme`. The system accent is the CSS `AccentColor` where `CSS.supports` it. Buttons get `.nv-accent` when the theme sets an accent (as on GTK). The text styles are inline CSS (`web_style_text`).
- **Linux GTK4:** `run` uses `GtkApplication` (no app id) and builds the root view in `activate`. The list is a `GtkListView` over a `GListModel` type registered at runtime with `g_type_register_static_simple`; the instance size comes from `g_type_query` and the `^List_Handle` sits right after the GObject fields. Model items are throwaway `GObject`s, because GTK only rebinds a row when its item object changes. Rows are recycled by the `GtkSignalListItemFactory` `setup`/`bind` signals. `GtkSingleSelection` autoselects row 0 at construction, so `_list_init` turns off `autoselect`, turns on `can-unselect` (without it the unselect is silently ignored) and unselects. `list_reload` emits `items-changed` with the previously reported count. `cells_created` starts around 200 because GtkListView pre-creates up to 200 row widgets for measuring, then recycles them. Under Hyprland, keys can be sent for testing with `hyprctl dispatch "hl.dsp.send_shortcut({mods='', key='Down', window='address:<addr>'})"`.
- **Windows (Win32):**
  - Layout only runs on `WM_SIZE`, so a content change that alters a natural size (`button_set_title`) calls `flex_relayout_ancestors`.
  - `_run` creates the main window hidden *before* building the root page, so every control can be created as a `WS_CHILD` of it (`g_windows.parking`). Row / Column re-parent their children afterwards. DPI awareness is PerMonitorV2, and `px` converts dp to px at the window's DPI. Fonts come from the DPI-scaled message font. On `WM_DPICHANGED` only the window rect follows: fonts and row heights keep their startup DPI.
  - The list is a `SysListView32` in virtual mode (`LVS_OWNERDATA`, report view, one column, no header, Explorer theme) inside an `NVList` container window. ListView caches its parent for `WM_NOTIFY` at creation, so it needs a parent that is never re-parented. `^List_Handle` reaches the container through `lpCreateParams` → `GWLP_USERDATA`.
  - Report view can't show two lines per row. `LVN_GETDISPINFOW` returns empty text, the theme paints hover and selection, and `NM_CUSTOMDRAW` draws the title and subtitle in `CDDS_ITEMPOSTPAINT`. The row height comes from a 1×h image list set as `LVSIL_SMALL`. `cells_created` stays 0.
  - `core:sys/windows` declares `NM_CUSTOMDRAW` as a `uintptr`, so `list_windows.odin` redeclares it as a `UINT`.
  - `windows/app.manifest` (embedded through `-resource:windows\app.rc`) enables Common Controls v6. Without it the controls are unthemed.
