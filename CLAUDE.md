# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
Experimental "native views" framework for Odin, targeting macOS, iOS, Android, Linux and Windows. It follows the Kotlin/Native approach: no codegen and no JS bridge. Odin code calls AppKit/UIKit directly through Objective-C interop, Android views through JNI, and GTK4 and Win32 through plain C bindings. Widgets so far: a vertically scrolling list (NSTableView / UITableView / ListView / GtkListView / SysListView32), a text label (optionally bold), a single-line text input (NSTextField / UITextField / EditText / GtkEntry / Edit), a push button (NSButton / UIButton / Button / GtkButton / Button), a custom-drawn canvas (NSView / UIView subclasses, a View subclass, GtkDrawingArea, a GDI+ window), an image loaded from bytes, a file or a URL (a drawn NSView subclass / a UIImageView subclass / an ImageView subclass / GtkDrawingArea / a GDI+ window; the canvas draws the same bitmaps), Flutter-style Row / Column stacks (NSStackView / UIStackView / LinearLayout / GtkBox / a hand-written layout window on Windows), a push/pop page stack (UINavigationController / the ActionBar's up arrow and the Back key / a back button in the title bar on macOS and GTK, an in-window bar on Windows), per-page bar actions (right bar button items / options menu items / GtkHeaderBar buttons / a trailing titlebar accessory / buttons in the Windows bar), and an in-view dialog, modal or not (a card over the page inside the window: NSBox / UIView / FrameLayout on the decor view / GtkOverlay child / a child window of the Windows host). The layout is Flutter-style: one shared app, framework backends per OS, and per-OS host folders that only handle packaging.

## Commands
- macOS: `macos/build.sh` (builds `build/macos/example` and runs it)
- iOS simulator: `ios/build.sh ["iPhone 17"]` (builds, bundles, ad-hoc signs, installs and launches with a console attached)
- Android: `android/build.sh [avd]` (default AVD `Pixel_10`; the `Pixel_8a` image is incomplete). It builds `libapp.so`, packages it without Gradle (javac → d8 → aapt2 → zipalign → apksigner), starts the emulator if needed, then installs and launches. App stdout goes to `adb logcat -s nv`. Screenshot with `adb exec-out screencap -p > build/android/shot.png`; `adb shell input tap/swipe` can drive the UI.
- Linux: `linux/build.sh` (builds `build/linux/example` against GTK4 and runs it). Only the GTK4 and libcurl runtimes are required: without `libgtk-4-dev` / `libcurl-dev` the script symlinks `libgtk-4.so.1` / `libcurl.so.4` into `build/linux/libs` for the linker. Under Hyprland, screenshot with `grim -g "$(hyprctl clients -j | jq -r '.[] | select(.class=="example") | "\(.at[0]),\(.at[1]) \(.size[0])x\(.size[1])"')" build/linux/shot.png` (select by class: the title changes with the page).
- Windows: `windows\build.bat` (builds `build\windows\example.exe` with the manifest from `windows\app.rc` embedded, then runs it with the console attached). To screenshot, get the window rect from `(Get-Process example).MainWindowHandle` with `GetWindowRect` (after `SetProcessDPIAware`) and use `System.Drawing.Graphics.CopyFromScreen`.
- Screenshot the simulator: `xcrun simctl io booted screenshot build/ios/shot.png`
- Type-check the framework:
  - macOS: `odin check nv -no-entry-point`
  - iOS: `odin check nv -no-entry-point -target:darwin_arm64 -subtarget:iphonesimulator`
  - Android: `odin check nv -no-entry-point -target:linux_arm64 -subtarget:android` (needs the `ODIN_ANDROID_*` env vars exported in `android/build.sh`; for a check only, any placeholder paths work)
  - Linux: `odin check nv -no-entry-point` on a Linux host, or add `-target:linux_amd64` elsewhere
  - Windows: `odin check nv -no-entry-point` on a Windows host

## Layout
- `app/`: shared user app. It must stay free of platform code.
- `nv/nv.odin`: the shared public API (`run`, `push`, `pop`, `Page`, `Page_Handle`, `Build_Proc`, `page_set_title`, `page_set_actions`, `Action`, `Icon`, `list_create`, `list_view`, `list_reload`, `Item`, `List`, `row_create`, `column_create`, `flex_create`, `Flex`, `Flex_Child`, `Axis`, `label_create`, `label_view`, `label_set_text`, `Label`, `Label_Handle`, `input_create`, `input_view`, `input_text`, `input_set_text`, `Input`, `Input_Handle`, `button_create`, `button_view`, `button_set_title`, `Button`, `Button_Handle`, `canvas_create`, `canvas_view`, `canvas_redraw`, `Canvas`, `Canvas_Handle`, `Painter`, `Color`, `Pointer`, the draw procs (`fill_rect`, `stroke_rect`, `draw_line`, `fill_ellipse`, `stroke_ellipse`, `draw_text`, `draw_image`), `Bitmap`, `bitmap_from_bytes`, `bitmap_from_file`, `bitmap_fetch`, `bitmap_free`, `image_create`, `image_view`, `image_set_bitmap`, `Image`, `Image_Handle`, `Fit`, `dialog_show`, `dialog_close`, `Dialog`, `Dialog_Button`, `Dialog_Handle`, and `View`, an opaque NSView*/UIView*/jobject/GtkWidget*/HWND). It forwards to `_run`, `_nav_push`, `_nav_pop`, `_nav_release`, `_nav_title_changed`, `_nav_actions_changed`, `_list_init`, `_list_reload`, `_flex_create`, `_label_init`, `_label_set_text`, `_input_init`, `_input_text`, `_input_set_text`, `_button_init`, `_button_set_title`, `_canvas_init`, `_canvas_redraw`, `_bitmap_decode`, `_bitmap_free`, `_image_init`, `_image_set_bitmap`, `_asset_read`, `_fetch_start` (`fetch_thread.odin` on all but Android, over `_http_get` / `_post_main`), `_dialog_show`, `_dialog_close`, `_dialog_set_hidden` and the `_`-prefixed draw procs, which each backend implements. `Item` is the list-row data struct; `Row` is reserved for the layout vocabulary. Every widget has one shape: `X` struct, `x_create(X) -> ^X_Handle`, `x_view(h)`, `x_set_y(h, ..)`. Only Row/Column return a plain `View` (no handle): children are fixed at creation, like Flutter. Pages follow the same shape: `run(Page)` / `push(Page) -> ^Page_Handle`, `Build_Proc` receives the handle, `page_set_title` / `page_set_actions(h, ..)`.
- `nv/*_macos.odin` / `appkit.odin` and `nv/*_ios.odin` / `uikit.odin`: the platform backends (`list_*`, `flex_*` for Row/Column, `label_*`, `input_*`, `button_*`, `canvas_*`, `image_*`, `nav_*`, `app_*`).
  - Each file body is wrapped in `when !IS_IOS { }` or `when IS_IOS { }`. Build tags cannot select the iOS subtarget (`darwin:iphone` parses but selects the wrong file).
  - `send`, `ns_string` and the Auto Layout helpers (`Layout_Constraint`, `flex_link_sizes`, `Layout_Anchor`, the `anchor_*` getters, `layout_pin_edges`, `layout_dialog_card`) in `appkit.odin` sit outside the `when` block and are shared by both backends, as is all of `cg.odin` (CoreGraphics bindings, the draw procs, and the image decode / download helpers). `objc_send` needs a typed receiver (`^NS.Object`, not `NS.id`).
- `nv/*_android.odin` / `jni.odin`: the Android backend (`#+build linux:android`). The Apple files carry `#+build darwin`.
- `nv/*_linux.odin` / `gtk.odin`: the Linux GTK4 backend (`#+build linux:default`). Unlike Darwin, the Linux subtarget build tags work, so no `when` split is needed.
- `nv/*_windows.odin` / `win32.odin`: the Windows backend (`#+build windows`). Bindings come from `core:sys/windows`; `win32.odin` holds the shared state (`g_windows`), helpers (`wstr`, `px`, fonts) and the few missing declarations.
- `nv/android/java/nv/`: the generic Java embedder. `NvActivity` loads `libapp.so`, forwards the Back key and the ActionBar's up arrow to `nativeOnBack`, and its options menu to `nativeOnCreateMenu` / `nativeOnAction`; `NvListAdapter` forwards `BaseAdapter` and click callbacks, and `NvInputListener` forwards `TextWatcher` / `OnEditorActionListener`, `NvClickListener` forwards `View.OnClickListener`, and `NvCanvasView` forwards `onDraw` / `onTouchEvent`, to exported `Java_nv_*` procs. Java is only used where Android requires a subclass.
- `macos/`, `ios/`, `android/`, `linux/`, `windows/`: host runners only (build scripts, `Info.plist`, `AndroidManifest.xml`).

## Backend patterns
- **Delegate classes:** ObjC classes are registered at runtime with `objc_allocateClassPair` and `class_addMethod`, using `proc "c"` IMPs and arm64 type encodings (for example `"q@:@"`).
  - The list data source stores a `^List_Handle` in its indexed ivars.
  - Each IMP restores `context = h.ctx` before calling Odin code.
- **App builder:** `run` takes a `build` proc because UIKit views can't exist before `UIApplicationMain`. `run` appends the root page to `g_nav` and calls `_run()`, which takes no arguments: each backend calls `nav_show_root()` (bracketed) once views can exist.
  - On iOS the root view sits in a plain container view pinned to its `safeAreaLayoutGuide`, since a stack view would slide under the navigation bar.
  - iOS uses the UIScene lifecycle. `NVSceneDelegate` is named in `ios/Info.plist`, and the names must match `app_ios.odin`.
  - Scene and app delegates are created by UIKit, so they use package globals (`g_app`) instead of ivars.
- **Row height:** on iOS rows are self-sizing and `item_height` is only an estimate. At a fixed 44pt, UIKit's subtitle configuration hides the secondary text.
- **Strings:** use `ns_string`, which copies and autoreleases. `initWithOdinString` does not copy.
- **Temp memory:** only `callback_exit` (`nv.odin`) calls `free_all(context.temp_allocator)`, when the outermost callback returns. Every entry from the platform that allocates or calls the app (`build`, row/select callbacks, `input_notify`, `button_notify`, `on_pop`, `on_close`, the back button / key handlers that call `pop`, the Win32 flex / nav / dialog `WM_SIZE`) is bracketed by `callback_enter()` / `defer callback_exit()`. `push`, `pop`, `dialog_show` and `dialog_close` themselves are app-called and don't bracket. Callbacks nest (an `on_click` that calls `input_set_text`, `list_reload` or `push`, a Win32 layout re-entering nested Row / Column procs), so an inner free would wipe the outer caller's strings. Procs the app calls never free.
- **`objc_send` arguments:** literals must be typed (`NS.BOOL(true)`, `NS.Integer(0)`), and nil object arguments are passed as `NS.id(nil)`.
- **Android startup:** Odin's `-build-mode:shared` never runs `_odin_entry_point` on the android subtarget. That entry point runs the `@init` procedures (without it `os.stdout` is nil and fmt prints nothing) and then the app's `main`. `jni_on_create` looks it up with `dlsym` and calls it; the `main` link name is reserved. It runs once per process: a later `onCreate` in the same process (relaunch after Back) only swaps the Activity global ref and calls `build` again through `set_content`. `android:configChanges` in the manifest keeps rotation from recreating the Activity.
- **Android build quirks:**
  - `core:thread` needs `pthread_setcancelstate`, which Android's libc lacks, so use raw `posix.pthread_create`.
  - The script links an empty stub `libpthread.a`.
  - Odin wants a `darwin-aarch64` NDK toolchain, so `ODIN_ANDROID_NDK_TOOLCHAIN` points at `darwin-x86_64`.
  - A stub `android_main` satisfies `native_app_glue`, which Odin always links.
- **Android JNI:** method IDs are looked up on each call (simple, not fast). `g_android.env` is refreshed in every JNI callback. `targetSdk` is 34 to avoid forced edge-to-edge (and `onBackPressed` still fires without `enableOnBackInvokedCallback`). `android_dp` converts dp to px from `DisplayMetrics.density` (read once through `jni_get_float_field`). The JNI table indices in `jni.odin` follow `struct JNINativeInterface` in the NDK's `jni.h`; check any new one there.
- **Row / Column (`flex_*.odin`):** `Axis` values equal the native orientation enums on every platform, so backends cast them directly (Windows has no native layout and uses the value as the main-axis index). The cross axis always stretches; `flex` 0 hugs, `flex` > 0 shares the spare main-axis space.
  - macOS/iOS: stack view with Fill distribution (`NSStackViewDistributionFill` is 0, GravityAreas is -1; UIKit's Fill is also 0). Cross-axis stretch is alignment `Width` (7) for a vertical stack / `Height` (8) for a horizontal one; UIKit's default alignment is already Fill. Flex children get hugging priority 1, others 1000, and `flex_link_sizes` adds `NSLayoutConstraint` multipliers between the flex children so weights are exact. NSStackView children need `translatesAutoresizingMaskIntoConstraints = NO` set explicitly; UIStackView does it itself. `text_field_label` is autoreleased, so `_label_init` retains it: every `*_create` returns an owned view.
  - Android: `LinearLayout` with `LinearLayout.LayoutParams(w, h, weight)`; a flex child has main-axis size 0 and `weight = flex`, a flex-0 child is `WRAP_CONTENT`, the cross axis is `MATCH_PARENT`. Spacing is a top/left margin (`setMargins`) in px on every child after the first. `setTypeface(null, BOLD)` is how a bold label goes bold without looking up `Typeface.DEFAULT_BOLD`.
  - Windows: an `NVFlex` window with a `Flex_Data` in `GWLP_USERDATA` lays out its children on `WM_SIZE`. Flex-0 children get their `measure` size (text extent in its own font for a `Static` label, stacked children for a nested flex, 0 otherwise), and the flex children split the spare space by cumulative weight, so the rounding error never adds up. `_flex_create` re-parents children with `SetParent`. `label_new(text, parent, style, font)` makes a Static (`g_windows.title` for a bold label and the bar title, `g_windows.font` otherwise).
- **Label (`label_*.odin`):** `Label.bold` is the heading style (bold 17pt / 20sp bold / GTK `title-4` / the Windows title font); plain is the system body font (15pt on macOS, 17pt on iOS, 16sp, a bare GtkLabel, the message font).
- **Dialog (`dialog_*.odin`):** `dialog_show(Dialog) -> ^Dialog_Handle` / `dialog_close(h)`. The body is built in `nv.odin` (`dialog_present`) from the framework's own widgets: a Column (spacing 12) of a bold title label, `content` (flex 0, so it must have a natural size) and a Row of `button_create` buttons (each flex 1, spacing 8) whose `on_click` is the `dialog_button_clicked` trampoline; the backends only add the card (padding 16dp, radius 12, width min(320dp, host − 32dp), centered, height from the body), the modal scrim (black at 40%) and hiding. Buttons never close the dialog: the callback gets the handle. `g_dialogs` holds the shown dialogs; `Dialog_Handle.page` is the top page at show time. Shown from inside a `build`, a dialog waits in `g_dialogs_pending` until `nav_present` shows the page. `nav_present` hides the page below's dialogs (`_dialog_set_hidden`), `nav_finish_pop` closes the popped page's dialogs first (`dialog_close_page`, before `_nav_release`) and unhides the page below's last. `dialog_close` removes the handle from `g_dialogs` before `_dialog_close`, so backends read `dialog_top_modal()` (the top page's visible modal dialog, contextless) for the state after. Modal blocking: the scrim takes the pointer everywhere; `action_notify` and `nav_back_notify` (the macOS / GTK / Windows back handlers) ignore clicks while `dialog_top_modal()` is set (the macOS and GTK bars are outside the scrim); Android's Back key closes the top modal dialog; Windows disables the page root and the bar controls; iOS covers the bar and turns off `interactivePopGestureRecognizer`. Keyboard: GTK makes the stack insensitive, Windows disables the page and focuses the first button, macOS makes the first button the first responder, iOS calls `endEditing:` on the host. A dialog closed while still pending gets its `on_close` too. The title and button handles leak like a popped page's widgets.
  - macOS: the card is a custom `NSBox` (`box_new`: type 4, no title, no border, zero content margins; `windowBackgroundColor` fill, corner radius 12) and the scrim another with a translucent fill, both subviews of `g_macos.content`, placed by `layout_dialog_card` (anchor constraints; width 320 at priority 999, at most host − 32). The body goes into the box's `contentView`. No subclass: AppKit hit-tests the topmost subview and sends an unhandled mouse event up the responder chain, never to a sibling. Closing retains + autoreleases before `removeFromSuperview` (the close runs from the card's own button) and autoreleases the body's own +1 (also on iOS).
  - iOS: host is the navigation controller's view, so the scrim covers the bar. `UIView`s with `layer.cornerRadius` 14; a `UIView` takes the touches on it. `_dialog_set_hidden(false)` also `bringSubviewToFront:`s them, since the controller may raise its bar during a transition. No keyboard avoidance yet.
  - Android: host is `getWindow().getDecorView()` (a FrameLayout over the ActionBar and content). The card is a `FrameLayout` with a `GradientDrawable` in the theme's `colorBackground` (`android_theme_color`: `Theme.resolveAttribute` into a `TypedValue`, `jni_call_bool` / `jni_get_int_field`), elevation 8dp, `LayoutParams(width, WRAP_CONTENT, Gravity.CENTER)`, width from `DisplayMetrics.widthPixels` (the decor view may be unmeasured). Scrim **and card** are `setClickable(true)`: a ViewGroup offers a touch to lower siblings when the top child ignores it. Hidden is `setVisibility(GONE)`. The relaunch path closes the root's dialogs before dropping its root.
  - Linux: a `GtkOverlay` between the window and the stack (`g_linux.overlay`); scrim and card are `GtkBox`es with the `nv-scrim` / `nv-dialog` classes from `NV_CSS` (`app_linux.odin`, one `GtkCssProvider` loaded with `gtk_css_provider_load_from_data`, which every GTK 4.x has, on the default display; GTK4's default theme has `@theme_base_color` etc. but no `.card`). The topmost widget gets the pointer and events bubble to ancestors only, so the scrim blocks the pointer; the keyboard is blocked by `gtk_widget_set_sensitive(false)` on the stack, the back button and the action buttons (`linux_dialog_apply_modal`); only a modal dialog grabs the focus. Both widgets are `g_object_ref_sink`ed and unreffed from `g_idle_add` after `gtk_overlay_remove_overlay`.
  - Windows: `NVScrim` is a black `WS_EX_LAYERED` child of the NVNav host at alpha 0x66 (layered children: Win8+); `NVDialog` holds the body (`SetParent`), cuts itself with `SetWindowRgn(CreateRoundRectRgn)` (declared in `win32.odin`) on `WM_SIZE` and paints a `RoundRect` border. Page roots get `WS_CLIPSIBLINGS` in `_nav_push`, and the bar's controls have it too, or their repaint would cover the overlay. `nav_layout` (no longer contextless: it measures the body) calls `dialog_layout`, which places the top page's visible dialogs and `SetWindowPos`es them to the top on every `WM_SIZE`. Modal: `dialog_apply_modal` (no arguments; from `dialog_top_modal()`) `EnableWindow`s the top page's root, `nav_back` and `nav_actions`, and `_nav_pop` runs it too for a page left disabled under another. Close clears the card's `GWLP_USERDATA` (the handle is freed before the destroy message lands), hides and posts `WM_NV_DESTROY` for both windows after moving the focus off the card.
  - Linux: `GtkBox`. GTK has no weights, so every flex > 0 child gets an equal share. The main-axis expand flag is set explicitly on every child: the list turns both flags on in `_list_init`, so a flex-0 list has to be turned off again, and an explicit value also stops the flag propagating up through the box.
- **Input (`input_*.odin`):** an `Input_Handle` like the list's. Backends report through `input_notify(h, h.input.on_change / on_submit)`, which reads the text into the temp allocator and does nothing while `h.silent` is set: `input_set_text` sets it because Win32, GTK and Android fire their change notification on a programmatic set.
  - macOS: `NSTextField textFieldWithString:` (retained), with an `NVInputDelegate` for `controlTextDidChange:` and `control:textView:doCommandBySelector:` (`insertNewline:` is submit). iOS: rounded `UITextField` with target-action on EditingChanged / EditingDidEndOnExit to an `NVInputTarget`. The public `Input` name avoids the AppKit binding `Text_Field`.
  - Android: single-line `EditText` with `IME_ACTION_DONE`. A hardware Enter reaches `onEditorAction` as key down and up, so only the down (or a null event from the soft keyboard) submits. Text comes back through `jni_string_clone` (GetStringUTFChars).
  - Linux: `GtkEntry`; "changed" and "activate" signals.
  - Windows: an `Edit` (`WS_EX_CLIENTEDGE`, cue banner as placeholder) inside an `NVInput` container, since Edit caches its parent for `EN_CHANGE`, like the list. Enter is caught by a `SetWindowSubclass` proc on `WM_CHAR`, which also swallows the beep. `measure` gives it the message font height + 7px.
- **Button (`button_*.odin`):** a `Button_Handle` like the input's; backends call `button_notify(h)`, which calls `on_click` and frees the temp allocator.
  - macOS: `NSButton buttonWithTitle:target:action:` (retained; the binding is `Button_View`, since `Button` is the public name) with an `NVButtonTarget`. iOS: `UIButton buttonWithType:` system (retained), `setTitle:forState:`, and target-action on TouchUpInside to an `NVButtonTarget`.
  - Android: `android.widget.Button` with an `NvClickListener`. Linux: `gtk_button_new_with_label` and the "clicked" signal.
  - Windows: a `BS_PUSHBUTTON` inside an `NVButton` container that receives `BN_CLICKED`. `measure` gives it `BCM_GETIDEALSIZE` width + 16px (at least 75px) and the message font height + 8px.
- **Canvas (`canvas_*.odin`):** `on_draw` gets a `Painter` valid only during the call; `canvas_redraw` invalidates. Units are points / dp with the origin top-left, and `draw_text` takes the top-left of the line box. No natural size (Windows `measure` gives 0), so it needs `flex` > 0. Backends call `canvas_draw_notify` / `canvas_pointer_notify`, which bracket the callbacks with `callback_enter` / `callback_exit`.
  - macOS / iOS: runtime `NVCanvasView` subclass of NSView / UIView (`^Canvas_Handle` in indexed ivars) overriding `drawRect:`. The macOS one is flipped and takes `mouseDown/Dragged/Up:`; iOS takes `touches*:withEvent:` and sets content mode Redraw. Text is `NSString drawAtPoint:withAttributes:`; only `canvas_font` / `canvas_color` differ per OS.
  - Android: `android.graphics.Canvas` over JNI, scaled by the density in `nativeOnDraw`. Two anti-aliased `Paint`s per canvas (`h.fill`, `h.stroke`) are recolored per call. Text baseline is `y - paint.ascent()` (`jni_call_float`).
  - Linux: `GtkDrawingArea` draw func with cairo (toy text API, baseline `y + ascent`); `GtkGestureDrag` for the pointer, which reports offsets from `gtk_gesture_drag_get_start_point`.
  - Windows: `NVCanvas` window, double-buffered `WM_PAINT` drawn with a minimal GDI+ flat-API binding (`GdiplusStartup` in `_run`), world transform scaled dp → px. Text uses GDI `TextOutW` via `GdipGetDC` with the message font at `px(size)`. The pointer is captured between `WM_LBUTTONDOWN` and `WM_LBUTTONUP`.
- **Image (`image_*.odin`, `fetch_thread.odin`):** a `Bitmap` is a decoded image with a reference count: `bitmap_free` drops a reference, and `image_create` / `image_set_bitmap` take one, so the app can free right after handing a bitmap over. `Image` shows `bitmap`, or else fetches `url` itself. `seq` drops a download that lost the race to a later `image_set_bitmap`. The natural size (`image_natural_size`) is `width` × `height` if given (one side keeps the aspect ratio), else the bitmap at 1 px per point / dp, else 0. `image_fit_rect` (Contain / Cover / Fill) serves the backends that draw the image themselves; the view clips a Cover overflow. Every handle keeps its own reference to its view, since a download can land after its page popped.
  - Loading: `bitmap_from_file` resolves a relative path against `assets/` next to the executable (`os.get_executable_directory`; inside the `.app` on iOS). Every build script copies `app/assets` there; Android packages it with `aapt2 -A` and reads it through `NvFetch.readAsset`. `bitmap_fetch` heap-allocates a `Fetch` (`runtime.heap_allocator()`, since the worker has its own context). Outside Android, `fetch_thread.odin` starts a self-cleaning `core:thread` running the backend's blocking `_http_get`, then `_post_main`. On the UI thread, `fetch_notify` (bracketed) decodes, calls `on_load` and frees the request.
  - macOS / iOS (`cg.odin`): ImageIO (`CGImageSourceCreateWithData` over an `NSData`) gives a `CGImageRef`. `_draw_image` flips the CTM inside the rect, because `CGContextDrawImage` draws bottom-up in these top-left contexts. Downloads use `NSData dataWithContentsOfURL:` inside `NS.scoped_autoreleasepool()`, and come back through `dispatch_async_f(&_dispatch_main_q, ..)` from libSystem, with no blocks. On macOS the widget is a drawn, flipped `NVImageView` NSView subclass, since NSImageView has no aspect fill. On iOS it is a `UIImageView` subclass with `contentMode` and `clipsToBounds`. Both override `intrinsicContentSize` (`"{CGSize=dd}@:"`).
  - Android: `BitmapFactory.decodeByteArray` produces a global ref that is never `recycle()`d. `draw_image` calls `drawBitmap(.., RectF, fill Paint)`; the paint is set opaque first, because its alpha would fade the image. The widget is `nv.NvImageView`, whose `onMeasure` uses `setNaturalSize` (px), since ImageView ignores `setMaxWidth` without `adjustViewBounds`; the `ScaleType` comes via `enum_value`. `NvFetch.start` downloads on a Java thread and posts `nativeOnFetch(req, byte[])` to the main Looper. The byte[] JNI helpers are `jni_byte_array` and `jni_bytes_clone`, and the manifest has `INTERNET`.
  - Linux: `gdk_texture_new_from_bytes` (GTK 4.6), then `gdk_texture_download` into a cairo ARGB32 surface, which is all the bitmap keeps. The widget is a `GtkDrawingArea` whose `content_width/height` is the natural size (GtkPicture can't be made smaller than its paintable). Downloads use libcurl easy (`curl_global_init` in `_run`, `NOSIGNAL`), with `g_idle_add` back to the UI thread.
  - Windows: `SHCreateMemStream` + `GdipCreateBitmapFromStream`. GDI+ keeps reading the stream, so it lives in `Bitmap.extra` until `_bitmap_free`. Drawing is `GdipDrawImageRect` with bicubic interpolation. The widget is an `NVImage` window painted like the canvas; `measure` returns `px(image_natural_size)`, and a new bitmap calls `flex_relayout_ancestors`. Downloads use WinINet (`InternetOpenUrlW`) and post `WM_NV_FETCHED` (`WM_APP + 2`) to the main window.
- **Navigation (`nav_*.odin`):** `g_nav: [dynamic]^Page_Handle` in `nv.odin` is the page stack (heap entries, so handles stay valid while the stack grows); `g_nav[0]` is the root page from `run` and the depth is `len(g_nav) - 1`. `run` and `push` make the handle (`nav_page_new`: clone the title, copy the actions), `push` appends it, builds the page (`nav_build`, which passes the handle to `build`) and calls `_nav_push`; a `push` from inside a `build` is queued in `g_nav_pending` and runs after that page is shown (`nav_flush_pending`), so pages stack in call order. `pop` removes the top entry, calls `_nav_pop(top, below)` (the native transition; `below` is already the top of `g_nav`; it returns false and the entry goes back when the platform refuses, which UIKit does mid-transition), then `nav_finish_pop`: `_nav_release` (drop the root view), `on_pop`, free the actions, the title and the handle (so `on_pop` is the last call the handle is valid for). `nav_system_pop` is the same without `_nav_pop`, for pops the platform already made. Backends never modify `g_nav`. Every backend has a `nav_update_chrome(e)` (Android: `android_chrome`) for the title, the back button and the actions, and `_nav_title_changed(h)` / `_nav_actions_changed(h)` for `page_set_title` / `page_set_actions` (separate, so a title change doesn't rebuild the action controls): the bar shows the top page only, so they act only when `h` is the top (iOS has a controller per page in `h.native` and updates any page). The setters skip the backend while `h.root` is nil: during `build` (because `_nav_push` follows) and after `_nav_release` (`nav_finish_pop` nils `root` and `native` before `on_pop`); the Android relaunch path nils the root before rebuilding for the same reason. `pop` inside a `build` is ignored, since the top page is the one being built. `pop` shadows the builtin inside the package, hence `builtin.pop(&g_nav)`. Widget handles have no destroy, so a popped page leaks its handles; only the view tree is released (Windows frees `Flex_Data` on `WM_NCDESTROY`). `pop` on the root page is a no-op (on Android the Back key then finishes the Activity).
  - **Page actions:** `Page.actions` (`[]Action`: title, `Icon`, `on_click`) are copied on `run` / `push` into `Page_Handle.actions` (`[dynamic]^Action_Handle`, freed in `nav_finish_pop`); `page_set_actions(h, ..)` replaces them. Every backend rebuilds the trailing controls from `e.actions` in its `nav_update_chrome` / `android_chrome`, so push and pop need nothing extra. `action_notify(h)` copies `on_click` / `user` out of the handle first: the callback may call `page_set_actions` or `pop`, which frees the handle. The backends find the handle from the control: the `tag` on Apple (one shared `nvAction:` IMP, `nav_action_clicked` in `appkit.odin`, restores `h.ctx`), the signal data on GTK, `GWLP_USERDATA` on Windows, menu item id = index + 1 on Android. Icons are per-backend `[Icon]` tables (`sf_symbol_names` in `appkit.odin`, `android_icon_names`, `gtk_icon_names`, `mdl2_glyphs`); an empty entry shows the title as text.
    - macOS: a second `NSTitlebarAccessoryViewController` (layout attribute Trailing, 6) with an `NSButton` per action (`buttonWithTitle:` / `buttonWithImage:` with an SF Symbol, textured rounded), recreated on every chrome update because AppKit sizes the accessory from its view's frame when it is added; the old container is retained + autoreleased before removal since the call may come from its own button's action. Both the back button and the actions target the one `NVNavTarget` (`g_macos.nav_target`, selectors `nvBack:` / `nvAction:`).
    - iOS: `UIBarButtonItem`s (`initWithTitle:` / `initWithImage:` with `systemImageNamed:`) on the controller's `navigationItem.rightBarButtonItems`, in **reverse** order because UIKit lays them out from the right; set in `page_controller_new`, which also stores the controller in `h.native` for `_nav_title_changed` / `_nav_actions_changed`. The old items array is retained + autoreleased before it is replaced. The target is `g_app.nav_target` (`NVNavTarget`, registered in `_run`).
    - Android: `onCreateOptionsMenu` → `nativeOnCreateMenu` adds `menu.add(0, i + 1, i, title)` items with `setShowAsAction(IF_ROOM)` and `setIcon(android.R.drawable.*)` (resource ids through `jni_get_static_int_field`); `onOptionsItemSelected` → `nativeOnAction(id)`. `android_chrome` (title, up arrow, menu; `android_show` is `setContentView` + `android_chrome`) calls `invalidateOptionsMenu`, which the framework defers, so the menu can be replaced from inside an item's own click.
    - Linux: `gtk_header_bar_pack_end` in **reverse** order (pack_end packs right to left). Each button is `g_object_ref_sink`ed and, on rebuild, removed from the header and unreffed from a `g_idle_add` callback: the rebuild often runs inside the button's own `clicked` emission.
    - Windows: `Button`s as children of the `NVNav` host (`g_windows.nav_actions`) with the handle in `GWLP_USERDATA`; icon buttons use `g_windows.icon_font` (Segoe MDL2 Assets at 4/3 of the message font, created only if `GetTextFaceW` confirms the face) and the glyph as caption. The bar now also shows on the root page when it has actions (`nav_bar_shown`); actions are right-aligned in `nav_layout`, icon buttons at least square. Old buttons are hidden and destroyed through `WM_NV_DESTROY`, like pages, after moving the focus off them; `nav_proc` only dispatches a `BN_CLICKED` whose sender is in `nav_actions`. `label_set_text` and `button_set_title` call `flex_relayout_ancestors` only when `measure` changed (the app may set text on every keystroke).
  - macOS: the pages are subviews of `g_macos.content`, a plain `NSView` that is the window's content view (so dialogs can sit above them), pinned by `layout_pin_page`: they fill it at priority 499, below the window size (500), so a page with no flex child ends short instead of shrinking the window; pages below the top are hidden. `g_macos` also keeps the window and the back button, a chevron `NSButton` (`imageWithSystemSymbolName:`, macOS 11+) in an `NSTitlebarAccessoryViewController` with layout attribute Leading (5), hidden on the root. `_nav_release` autoreleases rather than releases: when `pop` runs from the page's own button, `removeFromSuperview` already dropped the container's reference and the button's action is still on the stack.
  - iOS: each page is a `UIViewController` (`page_controller_new`: container pinned to the safe area, title) pushed on the `UINavigationController` in `g_app.nav`; the root goes into `initWithRootViewController:` directly. `NVNavDelegate` (`navigationController:didShowViewController:animated:`) trims `g_nav` to the controller count: after a programmatic `pop` the counts already match, after the back button or a swipe the Odin stack is one longer, and a cancelled swipe re-shows the same controller. `didShow`, not `willShow`, which also fires for a swipe that is then cancelled. `on_pop` for a gesture runs after the animation.
  - Android: `setContentView` + `setTitle` + `getActionBar().setDisplayHomeAsUpEnabled(depth > 0)` (`android_show`). Popped-under pages stay alive as global refs (`setContentView` removes the old content first, so a re-shown page has no stale parent). `nativeOnBack` returns false on the root so `super.onBackPressed()` finishes the Activity. A second `onCreate` in the same process resets the stack to the root (`nav_system_pop` for each pushed page, then the root's global ref is dropped and it is rebuilt).
  - Linux: a `GtkHeaderBar` as the titlebar (client-side decorations; it shows the window title) with a `go-previous-symbolic` button packed at the start, and a `GtkStack` with the Slide_Left_Right transition holding the pages. The stack owns a page from `gtk_stack_add_child` to `gtk_stack_remove`. A page popped while the slide runs is queued in `g_linux.dying` and removed on `notify::transition-running`, because removing it at once cuts it out of the animation and would finalize a button inside its own `clicked` emission.
  - Windows: `g_windows.root` is an `NVNav` host that fills the main window (`layout_root`); its bar (a `Button` "← Back" and a `Static` title in the title font, `g_windows.nav_back` / `nav_title`) is shown only on pushed pages, height `title_h + 12dp`. Page roots are created under `parking` and `SetParent`ed into the host (only the root moves, so the list / input / button containers keep their cached parents); pages below the top are hidden. `_nav_release` posts `WM_NV_DESTROY` (`WM_APP + 1`) so a page's own Back button finishes its `BN_CLICKED` before `DestroyWindow`; `_nav_pop` moves the focus to the main window first, and the Edit subclass removes itself on `WM_NCDESTROY`. The window caption follows the page title.
- **Linux GTK4:** `run` uses `GtkApplication` (no app id) and builds the root view in `activate`. The list is a `GtkListView` over a `GListModel` type registered at runtime with `g_type_register_static_simple`; the instance size comes from `g_type_query` and the `^List_Handle` sits right after the GObject fields. Model items are throwaway `GObject`s, because GTK only rebinds a row when its item object changes. Rows are recycled by the `GtkSignalListItemFactory` `setup`/`bind` signals. `GtkSingleSelection` autoselects row 0 at construction, so `_list_init` turns off `autoselect`, turns on `can-unselect` (without it the unselect is silently ignored) and unselects. `list_reload` emits `items-changed` with the previously reported count. `cells_created` starts around 200 because GtkListView pre-creates up to 200 row widgets for measuring, then recycles them. Under Hyprland, keys can be sent for testing with `hyprctl dispatch "hl.dsp.send_shortcut({mods='', key='Down', window='address:<addr>'})"`.
- **Windows (Win32):**
  - Layout only runs on `WM_SIZE`, so a content change that alters a natural size (`button_set_title`) calls `flex_relayout_ancestors`.
  - `_run` creates the main window hidden *before* building the root page, so every control can be created as a `WS_CHILD` of it (`g_windows.parking`). Row / Column re-parent their children afterwards. DPI awareness is PerMonitorV2, and `px` converts dp to px at the window's DPI. Fonts come from the DPI-scaled message font. On `WM_DPICHANGED` only the window rect follows: fonts and row heights keep their startup DPI.
  - The list is a `SysListView32` in virtual mode (`LVS_OWNERDATA`, report view, one column, no header, Explorer theme) inside an `NVList` container window. ListView caches its parent for `WM_NOTIFY` at creation, so it needs a parent that is never re-parented. `^List_Handle` reaches the container through `lpCreateParams` → `GWLP_USERDATA`.
  - Report view can't show two lines per row. `LVN_GETDISPINFOW` returns empty text, the theme paints hover and selection, and `NM_CUSTOMDRAW` draws the title and subtitle in `CDDS_ITEMPOSTPAINT`. The row height comes from a 1×h image list set as `LVSIL_SMALL`. `cells_created` stays 0.
  - `core:sys/windows` declares `NM_CUSTOMDRAW` as a `uintptr`, so `list_windows.odin` redeclares it as a `UINT`.
  - `windows/app.manifest` (embedded through `-resource:windows\app.rc`) enables Common Controls v6. Without it the controls are unthemed.
